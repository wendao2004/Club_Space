## 三、P1 —— 建议尽快修（1 项，已验证）

### 一局打完之后，只要大家点了"返回大厅"，这局的历史就没了

**证据链**

1. 存档写对了：`server/src/games/draw-rooms.ts:563` `archiveRound()` 在 `beginReveal` 之后落
   `draw_rounds`（每回合的画、词、谁猜对），上限 6000 点/回合（`:560`）。
2. 历史列表却是从**房间表**读的：`draw-rooms.ts:650-660`
   `SELECT ... FROM game_rooms WHERE kind='draw' AND status='finished'`。
3. 而"人走光了就删行"这条规则对 finished 的房间同样生效：
   `draw-rooms.ts:267-271` —— `players.length === 0` 就 `DELETE FROM game_rooms`，
   连注释都写着"斗地主/狼人杀同款处理"（那两个游戏没有历史功能，照搬才出了问题）。
4. 界面上"返回大厅再来一局"就是调 `leave`：`web/src/apps/DrawApp.vue:967` → `onLeave()`。

**复现（本地，干净库，3 人 1 轮）**

```
建房 200 · 阶段 finished
退出前，历史里有这局: true      存档回合数(draw_rounds): 3
最后一人退出: 404 房间已解散
退出后，历史里还有这局: false   退出后 draw_rounds 还剩: 3   game_rooms 这行还在吗: 0
```

**后果**：打一局、大家各自点"返回大厅"、最后一个人退出 → 这局的记录从历史里消失，
而它画的那些笔画还躺在 `draw_rounds` 里，再也**没有任何入口能查到**（详情接口按 room_id 找房间，房间已删 → 404）。
也就是说：数据没丢，但等于丢了，而且库里多出永远清不掉的孤儿行。

**改法（推荐 a，半天）**

- **a. 最小改动**：`leaveDrawRoom` 里判断 `row.status === 'finished'` 时不删行（改成 `status='archived'`）。
  大厅列表本来就只查 `waiting/playing`（`draw-rooms.ts:205`），不会因此多出幽灵房间；
  再补一条保留策略（见 P2-1）。
- **b. 更彻底**：历史从存档表聚合，房间删了也不影响。代价是要把 title / 结束时间 / 排名快照
  一起存进存档侧（新建 `draw_games` 或扩展 `draw_rounds`），列表与详情两处查询都要改。

选 a 还是 b，取决于你希望这份历史"活多久"（见文末拍板项 1）。

## 四、P2 —— 建议一月内做（5 项）

### P2-1 存档表只增不减，且房间一删就变孤儿

- **证据**：`db.ts:698-716` 建 `draw_rounds` 时**没有** `REFERENCES game_rooms(id)`，也没有任何清理代码
  （全仓搜 `DELETE FROM draw_rounds` 为 0 处）。
- **量级估算**：6000 点/回合 × 10 轮 ≈ 每局 1MB 级（点数按 JSON 存，实测空局几乎为 0）。
  一周打 10 局、一年 500 局 → 半 GB 左右，**不致命**，但它和 P1 的孤儿行叠在一起就说不清了。
- **改法**：① 存档只保留最近 N 局或 N 天（建议 90 天 / 最近 200 局，管理员可手动清空）；
  ② 清理时按 room_id 一次删干净；③ 顺手给 `draw_rounds` 补外键（或清理时兜底删孤儿）。

### P2-2 留言板的"标记已解决 / 删除"不留痕

- **证据**：`index.ts:4074-4081` 发帖写了审计；而 `index.ts:4086-4107` 的 resolve / delete
  **一条审计都没写**。整个项目里，这是唯一一处"破坏性操作零痕迹"的写路径。
- **为什么这在这套系统里算问题**：删活动那件事（`84476df`）专门写了"活动没了，谁在什么时候删的必须留痕"，
  留言板是同一个库里的另一个入口，标准不该不同。留言的定位还是"收集 bug 的工单"，删了没记录等于没证据。
- **改法**：两处各加一条 `audit({ category:'system', action:'board-resolve' | 'board-delete', target:id, payload:{ kind, resolved, noteLen } })`。
  半小时。
- 顺手清一处死代码：`board.ts:156-157` 的 `if (!current) throw 404` 永远不会成立（`getBoardPost` 自己就抛 404）。

### P2-3 那个 14.84GB 的单文件：规则上没问题，成本没人看见

- **线上事实**：`data/files/blobs` 共 **14.86GB / 14 个存块**，其中一个 **14.84GB**（其余都是几十 MB）。
  数据目录一天内从 26MB 涨到 15GB。库本身只有 772KB。
- **这是刻意设计**：`files.ts:405-450` 明确写了"不设单文件上限，只守磁盘余量（MIN_FREE_BYTES）"，
  理由是你原话"上传文件为什么有限制"。这一点我认同，不建议改回去。
- **但代价是隐形的**：① `backup.sh:225,242` 用 rsync 同步 blobs，备份盘从此每次都要吃下这 15GB；
  ② 迁移/换机/恢复演练的时间被这一个文件决定；③ 界面上**没有任何"谁用了多少空间"的视图**，
  要去 SSH 才知道盘子怎么满的。
- **改法（都不加限制）**：① 运维页加只读"存储用量"（总量 / 前 10 大文件 / 按人汇总）；
  ② 超过 1GB 的上传写一条审计（谁传的、多大），管理员能看到；
  ③ 部署指南的备份章节注明"备份目标至少留 2× 数据量"。

### P2-4 三个巨型文件还在继续长

- **证据**：`server/src/index.ts` **4363 行**（上一轮是 3556）、`web/src/apps/LedgerApp.vue` **3819 行**、
  `scripts/ui-smoke-test.mjs` **3702 行**；`DrawApp.vue` 一个月就长到 1739 行。
- 上一轮的结论是"不紧急，等批次稳定再拆"，现在批次稳定了，可以开始。
- **改法沿用上次**：`index.ts` 按 `games → assets → ledger → admin → chat → files → auth` 顺序搬，
  每步一次提交，用 `printRoutes()` 快照 diff 兜底。**只搬不改**。

### P2-5 测试的盲区，正是 P1 溜进来的原因

- **证据**：`draw-room-test.mjs:474-490` 断言了"刚打完那局出现在历史里"，但整个文件里没有
  "打完 → 全员 leave → 再查历史"。同理 `ui-smoke-test.mjs:3642` 的移动端只验了
  "外壳切过去了、没有任务栏"，**没有验任何一个应用在 390px 下能不能用**。
- **改法**：① 加一条打完就退的断言（这次 P1 的回归测试，本身就该有）；
  ② 移动端至少加两条"能看见画布 / 能点开留言"的断言。
- 这两个洞不补，同类问题还会再来一次 —— 它们不是"少测了一个函数"，是"少测了真实用法"。
