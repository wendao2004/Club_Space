# 系统优化方案（评审团结论）

> 评审时间：2026-10-20 ｜ 状态：**评审结论待审核；P0 四项与 P1 全部九项已按本方案实施并通过回归**
>
> 方法：5 个视角独立评审（安全 / 后端架构 / 前端体验 / 工程运维 / 产品），
> 各自只读代码、给出带 `文件:行号` 证据的结论；汇总时我做**去重、交叉验证与排序**，
> 并对关键结论逐条复核（见「四、我的复核结果」）。
> 原则：这是社团自用的单机 NAS 平台，**所有建议都以"不过度设计"为前置约束**。
>
> 实施进度见每项下的「状态」行。P0 四项已全部完成（全量回归 1633 项通过，不含浏览器套件）。

## 一、先说结论

系统底子比预期扎实：SQLite 用 WAL + busy_timeout、错误处理统一、上传是内容寻址 + 流式、
审计链有哈希、ops-runner 与 app 隔离且不共享 docker.sock、测试有 1800 条真断言。
**没有发现新的、可被匿名利用的 P0 漏洞。**

真正值得动手的是三类：

1. **"看起来安全，其实没有"的地方** —— 备份失败会被吞掉仍报成功、健康检查恒为 ok、
   登出后 SSE 还在推消息。这类问题最贵，因为它让人放弃警惕。
2. **几个便宜的严重隐患** —— 内网根 CA 私钥被一起挂进 Caddy、TOTP 登录限流是全站单桶
   （匿名就能锁死所有人登录）、工具内存闸门定得比容器上限还高。
3. **两块"重复实现"** —— 记账前端有两套写入逻辑（store 那份 0 调用）、
   文件浏览有 5 份、错误文案转换有 10 份。它们不影响今天，但会让每次改动都要改 N 处。

## 三、方案（按优先级，全部含验证方式）

### P0 — 建议本周做（4 项，合计约 2 天）

#### 1. 备份会"假成功"，并删掉还能用的旧备份
- **证据**：`deploy/backup.sh:157-159` 同步失败被 `|| true` 吞掉；`:194-197` 之后照常轮转删旧备份。
- **触发场景**：U 盘掉线/没插 —— `mkdir -p` 会在本地盘上凭空建出目录，
  脚本一路"成功"打印，而你以为备份在移动盘上。等真要用的时候，什么都没有。
- **改法**：同步后**比对源/目标对象数**；不一致立即非零退出、不轮转；
  备份目标必须是已挂载的独立设备（`findmnt` 校验）；轮转前先跑一次 canary 校验。
- **工作量**：小（半天）｜**验证**：把目标盘改只读/卸载后跑一次，必须非零退出且旧备份仍在。
- **状态**：已修复 —— 同步失败不再被 `|| true` 吞掉（rsync 失败才用 `cp` 兜底，两者都失败即退出）；
  同步后比对源/目标对象数；目标必须是 `findmnt` 确认的挂载点且设备号不同（取不到证据则 fail closed）；
  轮转前做金丝雀 + `quick_check` + 对象数三项自检，不过就不删旧备份。
  另外修了 `restore-drill.sh` 一个会让**每次演练都误报"备份损坏"**的解析 bug
  （`sqlite3` 默认用 `|` 分隔字段，而读取端按空白切分）。

#### 2. 工具内存闸门比容器上限还高，一次操作就能把全站打挂
- **证据**：`server/src/tools.ts` 单文件原为 **100MB**、合计 **256MB**；
  而 app 容器 `mem_limit: 512m`（`deploy/docker-compose.yml`）。
  `pdf-lib` 会整份读入并在内部再复制一份，`sharp` 未设 cache/concurrency（默认吃满 CPU 与 50MB 缓存）。
- **影响**：成员传一个 100MB 的 PDF 点一下"合并"，容器 OOM，**全平台下线**。
  这不需要任何漏洞，是个正常操作。
- **改法**：单文件降到 64MB、合计 128MB；`sharp.cache(false)` + `concurrency: 1`；
  Node 侧补 `--max-old-space-size=384` 让 GC 先动手（而不是被 cgroup 直接 SIGKILL）。
- **状态**：已修复 —— `MAX_INLINE_INPUT_BYTES = 64MB` / `MAX_INLINE_TOTAL_BYTES = 128MB`
  （`server/src/tools.ts`），sharp 在 `loadSharp()` 首次加载时统一配置，
  堆上限写在 `deploy/Dockerfile` 的 CMD 里。
- **工作量**：小（1 小时）｜**验证**：`image-tools-test`/`tools-extra-test`；再用 80MB PDF 观察 `docker stats` 峰值。

#### 3. TOTP 第二步登录限流是全站单桶 —— 匿名可锁死所有人
- **证据**：`server/src/index.ts:574` `enforceRateLimit(req,'totp',':login',true)`，第三个参数 `globalKey=true`；
  `index.ts:296` 在 globalKey 下键里**不含 IP**，全站共用一个桶；
  而 `ratelimit.ts` 对超限请求仍在计数，窗口被持续续期。
- **影响**：任何人无需凭据，每 15 分钟发 20 个伪造请求，**全站所有绑了 2FA 的账号第二步全部 429**——
  包括做运维必须用 TOTP 的管理员。持续发就能无限锁死。
- **改法**：键改为 `totp:login:<ip>`，账号维度另设 `totp:login:user:<uid>`（challenge 通过后已有 userId）。
- **工作量**：小（半小时）｜**验证**：`ratelimit-test` 补一条"两个 IP 互不影响"的断言。
- **状态**：已修复 —— 键改为 `totpLoginIp:<ip>:login`（60 次/15 分钟，容忍同一出口 NAT 后的集中登录）
  + `totp:login:user:<uid>`（20 次/15 分钟，challenge 验签后按账号计）。
  后者才是"密码已泄漏、TOTP 是最后一道防线"该守的维度，且换 IP 绕不过。
  新增 `scripts/totp-ratelimit-test.mjs`：用 `node:http` 的 `localAddress` 从
  127.0.0.x 发请求，真的模拟多个源 IP（普通 fetch 做不到，全站看起来都是 127.0.0.1）。
  **已反向验证**：把键改回全站单桶后，这个测试会失败 5 条（含"换 IP 仍能登录"）。

#### 4. 登出/强制下线不终止已建立的 SSE 连接
- **证据**：`server/src/index.ts:1437` 只在建连时 `requireUser`；`server/src/realtime.ts` 的连接表里没有会话标识；
  `server/src/auth.ts:128-140` 只删库里的会话行，不通知 realtime。
- **影响**：共用电脑上点了"登出"，那个标签页仍在收新消息与未读数；
  更严重的是**改口令/强制下线对已建立的流无效**，被偷的 EventSource 会一直收到新消息直到进程重启。
- **改法**：连接记录 sessionId；`destroySession`/`revokeAllSessions` 时关闭对应用户的连接；
  心跳里顺带复核会话是否仍有效。前端 `logout()` 同步 `realtime.stop()`。
- **工作量**：中（半天）｜**验证**：`realtime-test` 加"登出后 3 秒内不再收到事件"。
- **状态**：已修复 —— `Connection` 记录 `sessionId`；`destroySession` / `revokeAllSessions`
  分别调用 `disconnectSession` / `disconnectUser` 主动 `end()` 那条流；
  心跳（25 秒）顺带复核会话是否仍有效，作为漏网兜底（查不到证据时放行，
  避免 SQLite busy 时把全站踢下线）；前端 `logout()` / `handleUnauthorized()`
  先 `useRealtime().disconnect()`，不让 EventSource 在 cookie 失效后反复重连。
  实测：去掉主动断开后，`realtime-test` 新增的两条断言都会失败（心跳兜底要等 25 秒），
  说明"主动关闭"确实是必要的，而不是有兜底就可以省。

### P2 — 有空再做（不做也不影响使用）

**后端**：迁移加锁后重读版本（多实例才需要，3 行）；SSE 心跳不再写库（现在 100 连接 = 4 次/秒 WAL fsync）；
`audit.ts` 注释说"有触发器禁止改删"但实际没有，补触发器或改注释。

**前端**：`api.ts` 按域拆分（现在 1531 行混装传输/类型/格式化，53 处 import）；
错误文案转换统一到 `lib/errors.ts`；`useNarrow`/`useFileBrowser` 抽 composable（4 处各写一遍）；
104 处硬编码颜色归一；聊天列表 `.msg{content-visibility:auto}`（别上虚拟列表）；
壁纸加 ETag/缓存。

**运维**：`.env` 要求 `chmod 600`；`gen-certs.sh` 默认 8443 与 `.env.example` 的 9443 不一致（引导页链接会错）；
README 测试数 1801 vs 表内合计 1811；证书 2027-11 到期无提醒（可以在健康检查里带上剩余天数）。

## 五、产品侧：需求对照与"最后一公里"

| 原始需求 | 完成度 | 缺口 |
|---|---|---|
| 工具集 | ~62% | 23 个工具可跑；**视频剪辑 0**（已改标「规划中」并说明原因，不再假装可用）、**在线表格 0**；Word/Excel/PPT→PDF 依赖外部服务 |

| 记账 | ~95% | 状态机、凭证、导出都有；**已有待办角标与一键筛选**（提交/审批/被驳回→桌面、开始菜单、任务栏、移动端） |
| 娱乐 | 3/4 | 象棋、斗地主、狼人杀；**三国杀 0** |
| 桌面 UI | ~90% | 多窗口/贴边/任务栏都有 |

**最值得补的四件（都是"功能已有但用起来会卡住"）**：

1. **转换服务启停链路** ✅（已做：白名单默认清空，运维页直接写出该跑的命令；失败信息里也带上了
   `docker compose -f docker-compose.yml -f heavy-tools.compose.yml --profile convert up -d convert`）。
   选的是"界面上诚实说明 + 给出命令"，而不是让 ops-runner 跨 compose 文件操作 —— 后者要动
   `ops-runner` 的挂载与白名单校验，收益不抵风险。
2. **视频工具名不副实** ✅（已做：`media.transcode` 的 `availability()` 无条件返回不可用并写清
   "配 URL 也不会变可用，那个地址接的 Gotenberg 没有 ffmpeg"）。
3. **Office/CSV 预览**（高/中，**未做**）：现在 docx/xlsx 只能下载；可以复用转换服务转 PDF 后预览。
   留到下一批：它需要前端新的预览器 + 转换服务常驻，是一次独立改动。
4. **记账/借还待办角标** ✅（已做：`GET /api/todos` 一个聚合接口，桌面图标 / 开始菜单 / 任务栏 /

**明确不建议做**：浏览器端多轨视频剪辑（8GB NAS 撑不住，服务端 ffmpeg 任务才是正解）、
PDF→Word / PDF 加密（现有 MIT 库做不到，硬上要引 AGPL 或重容器）、公网推送与常驻通话、
把三国杀和在线表格当成近期目标（各自都是大工程，要做就单独立项）。

## 六、建议的执行批次

**批次 1（本周，约 2 天）**：P0 的 4 项全部做完。
它们的共同点是**改动极小、风险极低、收益是"防止一次事故"**。
验证：`pnpm typecheck` + 相关套件 + 备份故障注入一次。

**批次 2（两周内，约 3-4 天）**：P1 的 1/2/3/4/8 项（都是小改动）+ P1 的 9 项（弹层统一）。
理由：先把"看不见的坑"填掉，再动体验。

**批次 3（一月内，约 1 周）**：P1 的 5/6/7 项（聊天 N+1、升级回滚、CI 对齐）+ 产品四件。
P1-5/6/7 与产品 1/2/4 均已完成；产品 3（Office/CSV 预览）未做 —— 它需要前端新预览器
外加转换服务常驻，是一次独立改动，已单列。

**批次 4（看心情）**：P2 里挑顺手的。**P2 不做完全不影响使用**。

**架构层面**：`server/src/index.ts` 3556 行拆分值得做，但必须"只搬不改、一步一提交"，
按 `games → assets → ledger → admin → chat → files → auth` 的顺序，每步用 `printRoutes()` 快照 diff 兜底。
这件事**不紧急**，等批次 1-3 稳定后再动。

## 七、需要你拍板的四件事

1. **P0 四项是否本周就做？**（我建议做，尤其备份和 TOTP 限流——一个会让你丢数据，一个能让全站登不进去）
