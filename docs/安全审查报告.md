# 安全审查报告

一夜之间写完 3 万行代码，然后让 7 个独立 agent 对高风险面做对抗式审查，
每条发现再交由另一个 agent **尝试反驳**（默认立场是"这条站不住"）。

**结果：报告 36 条，20 条进入反驳验证，17 条确认成立，3 条被驳回。**

被驳回的 3 条也很重要 —— 它们说明这套流程不是"什么都信"：
其中一条声称"SVG 内联预览会导致 XSS"的反驳理由是"Caddy 已配 script-src 'self'，
内联脚本不会执行"（但**仍然修了**，理由见下），
另外两条的核心前提经代码核验是事实相反的。

---

## 三条 blocker（都已修复）

### 1. 秒传漏记引用计数 → 删一个副本会把别人的文件一起删掉

**这是今晚最严重的一条**，因为它的后果是**静默的数据丢失**。

- 存储是内容寻址的：同一份内容在磁盘上只有一份，多个"节点"引用它
- 秒传会为已存在的内容直接建节点，但**忘了给引用计数 +1**
- 于是删掉任何一个引用者时计数就归零，blob 被真正删盘 —— 而另一个引用者还在

**触发路径简单到令人不安**：自己上传一份文件 → 把同一份内容秒传到另一个目录 →
删掉那个副本 → **原始那份也打不开了**。跨用户同理。

**修复**：秒传分支先 `retainBlob` 再建节点，放在同一个事务里。
另外加了一个引用计数自检接口（`auditBlobRefCounts`），管理员打开存储面板时会比对
"每个 blob 的 refs 是否等于引用它的未删节点数"。

**回归测试**：`e2e-test.mjs` 的「秒传的引用计数（防误删回归）」。

---

### 2. 拿到管理员会话就能把两步验证换成自己的

TOTP 存在的意义是"即使口令泄漏，攻击者也进不来"。但 `setup`/`enable`
只要求"当前是管理员"—— 任何拿到会话的人都能：

1. 调 `setup` 拿到一个**明文返回的**新秘密
2. 用自己的验证器算一个码
3. 调 `enable`，服务端用**它自己刚发出去的那个秘密**校验通过
4. 原绑定被静默覆盖成攻击者的

之后攻击者可以自造动态口令通过门禁，一路走到 Docker 管控（= 宿主机 root）。
**2FA 本来要挡的就是这件事，结果被完整复现。**

**修复**：账号**已绑定**时，重新绑定必须先证明对现有因子的占有 ——
提交当前验证器上的码，或账号口令，二者其一。
另外给 `setup`/`disable` 都补上了限流（`disable` 原本一点限流都没有，
6 位码可以被暴力枚举）。

**回归测试**：`admin-e2e-test.mjs` 的「重新绑定两步验证（防会话劫持回归）」。

---

### 3. 发牌种子能从公开的房间 id 推出来 → 任何玩家都能算出所有人的手牌

斗地主的整个设计建立在"手牌是隐藏信息"上，而这条把那个前提**完全推翻**了。

```js
// 旧代码：从房间 id 派生种子
const seed = Number.parseInt(row.id.replace(/\D/g, '').slice(0, 8), 36)
```

房间 id 是**公开发给每个参与者**的（视图里有、URL 里有），而洗牌是纯函数。
于是任何在座玩家取出 id、跑一遍同样的 `createDeck()` + `shuffle(seed)` + `deal()`，
就能得到三家全部 17 张手牌和三张底牌。

而表面上一切正常 —— 服务端确实"只发给你自己的手牌"，
只是那个手牌是对手也能算出来的。

**修复**：改用 `crypto.randomInt` 取种子，并且种子只存在服务端 state 里
（`toDoudizhuView` 不会把它发出去）。

## 已确认的 minor（也都修了）

- **重复提交同一张牌的 id**：`[id,id,id,id]` 会被按点数算成"四个相同"= 炸弹 ——
  一张 3 就能当炸弹出。已加去重 + 按数量核对。
- **聊天发言无频率限制**（`chatSend` 规则定义了但没挂上）：一条消息还要触发 FTS 索引、
  对每个成员算一次未读聚合、各推一次 SSE，刷屏能把单核打满。
- **上传发起无限流**。
- **TOTP `disable` 无限流**：可以暴力枚举 6 位码把 2FA 摘掉。

## 被驳回的 3 条（说明流程没有"什么都信"）

1. 一条声称"TOTP disable 的暴力破解构成 major" —— 缺陷本身属实（确实没限流），
   但**严重度被夸大**：登录根本不校验 TOTP，所以关掉它不带来任何新能力；
   而且拿不到 TOTP 码的攻击者本来就可以直接重绑（那才是真问题）。降为 minor，仍然修了。

2. 一条声称"叫地主阶段退房会让对局永久卡死" —— 反驳者核验代码后发现前提事实相反。

3. 一条关于 SVG 的发现被驳回，理由是"Caddy 已配 `script-src 'self'`，
   内联脚本不会执行"。**但这条反驳只对了一半**：CSP 是部署配置，可能被改动、
   也可能有人在没有 Caddy 的情况下直接暴露 Node 端口。所以 SVG 仍然改成了
   attachment —— 代码层的保证比配置层的更可靠。

## 第二轮：验证这些修复本身（12 个 agent）

修完之后我又跑了一轮：每处修复交给一个独立 agent 验证，默认立场是
"**这个修复有问题**"——因为仓促的修复很容易引入新问题，或者根本没修到点上。

结果：**有 3 处修复不完整，其中 2 处是 major。**

### 我修错的 3 件事

**1. TOTP 重绑定的修复没修到点上（major）**

我加的门禁是"提交当前动态口令**或**登录口令"。但登录接口本身不校验 TOTP ——
也就是说"知道口令"既能拿到会话，又能通过这个门禁换掉第二因子。
**2FA 想挡的"口令泄漏"威胁原样还在。**

正确做法：已绑定且秘密可解密时，**只接受动态口令**。
只有"秘密已无法解密"（换过 `WL_SESSION_SECRET`）这种第二因子本就失效的状态，
才允许用口令恢复。

**2. 加了服务端校验，却忘了改前端（major）**

服务端要求提交 `currentCode`，而前端 `totpSetup()` 永远发 `{}`。
结果是：界面上点"重新绑定"必然 403，而 `broken` 状态下 UI 明明提示
"请关闭后重新绑定"——那个操作在界面上根本走不到，管理员会被永久挡在运维之外。

这条是"改一半"的典型：服务端改了，客户端没跟上，测试也没覆盖到 UI 路径。

**3. 引用计数的修复只修了一处（major）**

秒传分支修好了，但 `completeUpload` 与 `saveBufferAsNode` 里
`retainBlob` 与建节点**仍是裸的两步**（不在同一事务里）。如果建节点抛错
（同名冲突），引用计数已经 +1 但没有节点产生 —— 这份内容永远不会被释放，
blob 文件永久滞留在磁盘上。验证者实测复现了这一点。

顺带发现：我写的 `auditBlobRefCounts` **从来没被调用过**（死代码），
而且它的 SQL 只从 `blobs` 表出发，**恰恰漏掉了它最该抓的那件事** ——
"节点还在引用但 blob 行已经没了"（也就是数据已经丢了的终态）。
等于装了烟雾报警器却没接电源。

### 第二轮之后我改掉的根因

审查指出：**登录不校验 TOTP** 是那个"口令泄漏 = 账号沦陷"问题的根因 ——
第二因子只保护了"账号里的某些操作"，而攻击者拿到账号后能做的事远不止那些。

这一点我改了。现在的登录是**两步**：

1. 口令正确时，若账号绑定了两步验证，服务端**不发会话**，只返回一个
   短效的挑战令牌（HMAC 签名、5 分钟有效、一次性）
2. 用挑战令牌 + 动态口令换真正的会话

顺带修了一个可用性细节：动态口令打错时**不消费**挑战令牌，
否则用户手滑一位就得退回去重输口令。暴力试的代价由限流承担。

**这一步之后，TOTP 才真正成为第二因子。**

### 仍然存在的限制

诚实列出：

- **第二因子只在"进入账号"和"运维操作"两处校验**。日常操作（发消息、传文件、
  记账）不要求动态口令 —— 那是刻意的：如果每做一个动作都要掏手机，
  大家会想办法绕过整个机制。会话本身是第二因子校验后的产物。
- **修复验证覆盖的是"我能想到的 12 处"**，不是全部。第一轮 16 条 minor 没有做反驳验证。
- **仍然没有动态渗透测试**，也没有压力测试。
- **没有审查部署脚本**（compose、Caddyfile、证书脚本、备份脚本）——
  它们从未真实运行过，静态审查的价值有限。

---

## 这次审查没能覆盖的

诚实说明：

- **只做了静态审查**，没有动态渗透测试（没有可运行的目标环境）。
- **依赖漏洞只凭知识判断**，没有联网查 CVE（本机拿不到 GitHub / npm 官方源）。
  需要你在有网环境跑一次 `pnpm audit`。
- **没有审查部署脚本**（`deploy/` 下的 compose、Caddyfile、证书脚本、备份脚本）——
  它们没有真实运行过，所以静态审查的价值有限。
- **前端只做了横向检查**（XSS / v-html / CSRF），没有逐组件审。
- **DoS 只覆盖了最明显的几条**，没有做压力测试。

## 建议你之后做的事

1. 在 NAS 上部署后，用 `pnpm audit` 与 `docker scout` 之类查一次依赖
2. 加一条定期的审计链外部锚定（把链头写到 NAS 之外的介质）——
   这是"可检测的不可篡改"里唯一还没落地的部分
3. 如果社团里有懂安全的人，让他按这份报告复核一遍修复是否到位
