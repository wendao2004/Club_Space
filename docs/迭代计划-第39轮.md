## 一、为什么本轮不加功能

五项需求全部已实现（docs/需求.md vs README.md:12）。最近的故障不是「功能没做」，
而是**同一类失败反复发生：改了，但用户真实走的那条路上没有人测**。

评审自己的结论（docs/优化方案评审-20261021.md:143-150）原话是：
「它们不是少测了一个函数，是少测了真实用法」。同类事故在此后继续发生：

| 事故 | 证据 |
|---|---|
| 打完就退，历史对局消失 | 优化方案评审-20261021.md:63-97（P1，已验证可复现） |
| 重开窗口后第一次点白板空白 | 部署记录.md（第二十八轮） |
| 保存后切板内容丢 | 部署记录.md:752-768 |
| 观察者画布 300×150（别人看是点点点） | 迭代记录.md:159-190 |
| 拖不动进度条（Range 未实现） | 迭代记录.md:117-148 |

同时，用户反馈侧**没有积压**：部署记录.md:850-1124 记录的第三十一至三十八轮，
每一条反馈都已闭环，没有开放项。所以「必要」档不该由「还有人骂」来填，
而应由「下一次会出事」来填。

## 三、逐条执行方案与验收

**验收通则**：每条断言都必须能在「把修复回退」时变红。这是本仓库既有风格
（先例：部署记录.md:768「反向验证过：回退修复后…立刻失败」）。

### 第 1 批 — 不碰 ui-smoke（--skip-ui 基线 8018 条 / 222s）

**R1 · 留言板发帖限流**

- 现状：routes/board.ts:42（POST）**没有任何 checkRateLimit**；routes/*.ts 内 RateLimit 命中数为 **0**
- 做法：RATE_RULES.boardPost = { windowMs: 3_600_000, max: 30 }，路由内按 **userId** 判断
- ⚠️ **不可按 IP**：enforceRateLimit 默认拼 IP（index.ts:322）。同一 NAT 下的办公室会撞限流，
  ratelimit.ts:88-100 记着前车之鉴（TOTP 原本设 10 次，正常流程就会撞）
- 真实收益不是安全而是性能：broadcast({ type:'board' })（routes/board.ts:104）会让
  **每个在线者各重拉一次列表**（web/src/stores/board.ts:57）
- 验收：board-test.mjs 加「连发 31 条 → 第 31 条 429」+「换账号仍可发」；去掉限流后该断言变红

**R2 · enforceRateLimit 迁出**

- 现状：index.ts:315 **未 export**，被 7 个章节共用（认证 5 次、文件、上传、聊天、三款游戏、管理员 4 次）
- 做法：迁到 routes/auth-guard.ts 并 export（约 25 行搬迁）
- 验收：WL_DUMP_ROUTES=1 快照 **147 行逐条一致** + pnpm -F @wl/server typecheck exit 0

**E1（API 侧）**

- E1a「打完 → 全员离开 → 再查历史」→ draw-room-test.mjs（该文件已有「打完就退」雏形）
- E1b 限流反向断言 → board-test.mjs

### 第 2 批 — 只动 1 条 ui-smoke 断言（单次 252s，控制重跑次数）

## 五、本轮三个决策及其依据

### 决策 1 · index.ts 本轮不拆（与既有评审建议相反）

评审（优化方案评审-20261021.md:191 拍板项 3）建议「继续按同模式拆」。工程架构师复核后反对，
证据三条：

- **拆分与「往里塞」同时发生，净效应被抵消**：34edb6b 拆完 4363 → 4134，
  但到 cfa14b5 又回到 **4250（+116 行）**——1f44bae 加了 37 行听歌房流通道、7d15a2c 加了 59 行 Range 实现
- **真正的成本是搬迁前置任务**：enforceRateLimit（index.ts:315）未 export、被 7 个章节共用，
  依赖 audit + currentUser + HttpError。拆任何一节都要先搬它
- **循环依赖风险**：5 个定时器（:4082/4103/4124/4149/4168）直接调用路由模块内的推送 helper。
  搬游戏章节需先迁 pushXiangqiRoom / scheduleBotReply / healStalledBotTurn + pendingBotReplies

**结论**：本轮不做，改走两条低成本替代 —— ①确立规则「新路由一律进 routes/」（零成本，立刻止住净增长）；
②只把 enforceRateLimit 迁出（本轮 R2），为后续限流提供正确落点。

**推翻条件**：若接下来要同时改动游戏域或记账域的多条路由，拆分就从「重构」变成「改动前置」，那时才该先拆。

### 决策 2 · 手机端先保留全部入口，只加标注

没有任何移动端真实使用证据（全仓 analytics|埋点|telemetry 基本为 0）。
在无证据的情况下下架入口，等于用一个猜测换掉另一个猜测。
标注「请在电脑上使用」符合本仓库既有原则：宁可如实标注，也不要空壳。

**推翻条件**：若真机走查确认手机上确实没人用这些应用，或确认有人天天用手机传文件，
结论立刻翻转（前者可下架，后者必须做适配而非标注）。

### 决策 3 · 限流拆成两半：留言板做，画笔延后

- 留言板：真实收益是**性能**（每帖一次全站 broadcast 重拉），非安全；成本 +2 行 → **做**
- 画笔：阈值定错的代价（偶发丢笔）远超收益，且 draw-room-test.mjs 24 处 strokes 调用的
  实际速率**未测量** → **先量再定**

## 六、遗留待办（本轮不做，需另行决定）

1. **备份离机盘** —— 唯一不可逆损失面，且 100% 未落地：
   WL_BACKUP_TARGET 未配（部署记录.md:494）、手动快照明确不含 15GB blobs、
   sqlite3 缺失导致 restore-drill.sh 在这台机器上跑不了（部署记录.md:153）。
   这是物理动作（要不要接一块离机盘），不是工程量。
2. **D1 画笔限流** —— 先量 draw-room-test.mjs 24 处 strokes 的实际间隔。
   若本就密集连续，本项从「小」变「中」，且可能要先改测试再上线。
3. **D2 聊天文件消息开预览** —— 前置为 GET /api/files/:id
   （复用 getNode:130 + canRead:151）。风险：新增读文件入口若不复用 canRead 即权限泄露。
4. **聊天传文件（「发送到…」）是否值得做** —— 现状 sendFile（stores/chat.ts:357）
   在 web/src **只有定义、零调用点**。最便宜的取证是只读 SQL：
   SELECT COUNT(*) FROM messages WHERE kind='file'。若长期为 0，直接降为不做，别做半成品。
5. **使用可见性** —— 目前没有任何人能回答「听歌房这 4 轮到底有没有人用」。
   建议后续加最小的「某用户某天打开过某应用」记录（内部 8 人社团，隐私不是障碍）。
