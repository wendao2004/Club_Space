# 第 41 轮：听歌房在线曲目进队列（本地多人同步播放）

**目标**：把哔哩哔哩在线曲目从"单人试听"升级为"能排进队列、全厅同步播放"。
**非目标**：不做逐字节音频同步（沿用第 33-35 轮已经验证过的权威位置模型）；不做版权限制（用户已明确"法律风险不用管"）。

## 一、核心判断：同步机制一行都不用新写

听歌房现有的同步模型是：服务端只持有"当前曲目 + `startedAt` + `playedToken` + 暂停位置"，
`positionMs` 由服务端算（`server/src/music.ts:190-238`）；客户端拉 `/api/music/time` 校准时钟，
再每 500ms 用 `player.enforce(np)` 校正本地 `<audio>`：偏差 40ms 内不动、400ms 内调速、更大才 seek
（`web/src/apps/MusicRoomApp.vue:147-179`，第 35 轮实测 11ms 量级）。

这个模型**只依赖"一个能 seek 的音频 URL"**，完全不关心音频来自 nodes 表还是外网站点。
所以本轮的正确做法不是"为在线曲目设计一套新同步"，而是：

> 让在线曲目变成一种**普通的房间曲目**，然后白拿这套已经调准过的同步。

唯一需要新设计的，是"这个 URL 的首字节有多快、有多稳"——也就是延迟。

## 二、延迟预算：钱花在哪三步上

一次"切到在线曲目"实际由三段耗时组成：

| 段 | 现状 | 手段 |
|---|---|---|
| ① 解析 playurl（bvid → 带签名的音频 URL） | ~300-600ms，已有 10 分钟解析缓存 | **预热**：入队/切歌时就把队列头的解析做完，切歌时命中缓存 |
| ② 拉首字节（上游 CDN，每个 Range 请求一次 RTT） | 200-500ms，且拖动进度条 = 一次新的 RTT | **磁盘缓存**：整首落盘，命中后 Range 由本地磁盘回答 |
| ③ 客户端对齐（seek 到服务端位置） | 已有 40ms 死区 + 调速 | 不新增 |

②是最大且最不可控的一项：8 个人同时听，就是 8 条上游连接、每秒几十个 Range 请求，
既抖又容易踩风控（第 40 轮已经吃过 412 和"首页零 cookie"）。
**把整首（2-6MB）落盘一次，之后所有人所有 seek 都读本地**，是把抖动从"外网变量"变成"磁盘常量"的唯一办法。

### 磁盘缓存规则（`server/src/music-online.ts`）

- 路径：`<data>/tmp/online-audio/<bvid>.m4a`；大小上限 `ONLINE_CACHE_MAX_BYTES = 2GiB`，超限按 mtime 最旧先删（NAS 余量 859G，2GiB 只是防止被当下载器）。
- 命中：直接从磁盘发流，`206` + `content-range` + `accept-ranges`，**不再解析上游**（解析缓存也只有 10 分钟，但它不再是关键路径）。
- 未命中：照旧代理上游，同时把字节 tee 到 `<bvid>.part`，下满 rename；中途断开删 `.part`。
- 磁盘满 / 只读：catch 后继续纯代理。降级，不是失败——缓存是优化项，不能成为可用性的前置条件。

## 三、数据模型（schema v22）

现在 `music_queue.node_id` 有 `REFERENCES nodes(id)` 外键、非空；在线曲目不是节点，塞不进去。
迁移里重建两张表（SQLite 不能改列约束），并保留既有行与索引：

- `music_queue`：`node_id` 保留（改成"不透明引用符"），新增 `source TEXT NOT NULL DEFAULT 'file' CHECK(source IN ('file','online'))`、`online_title TEXT`，**去掉 nodes 外键**。
- `music_state`（单行）：同样加 `source` / `online_title`。
- 引用符：文件曲目 = nodes.id 原样；在线曲目 = `bi:BVxxxxxxxxxx`（`parseOnlineTrackId` 已有）。
- **对外字段名不变**（`nodeId` 仍是那个字符串），所以前端改动被压到"选流地址"一处；新增 `source` 字段供显示。

### 两个必须顺手修掉的坑

1. `healDeletedCurrent()`（`server/src/music.ts:177-188`）用"nodes 里查不到=已删除"判定僵尸曲目。在线曲目在 nodes 里查不到，会被**立刻切歌**。必须只对 `source='file'` 生效。
2. `QUEUE_SELECT`（`server/src/music.ts:162-168`）是 `JOIN nodes`，在线曲目会被 JOIN 掉、静默不出现在队列里。改成 `LEFT JOIN nodes` + `COALESCE(n.name, q.online_title)`。

这两个坑的共同形态是"在线引用符被当成节点处理"——这也是本轮唯一的真实风险点。

## 四、权限

- 排歌：文件曲目仍要 `canRead`（沿用 `enqueueTrack`）；**在线曲目任何在厅成员都能排**（它不在文件区，没有空间/私有语义）。
- 切歌 / 暂停 / 移出队列：沿用现有规则（在厅成员可切歌暂停，移出仅本人或管理员）。
- 流授权：`/api/music/online/stream` 维持现状（登录即可，试听与播放同一条路），不新增门禁——把门禁加在"能否进队列"，不要加在"能否读字节"，否则刚切歌时慢设备的在途 Range 会变成 403，正是 `RECENT_GRACE_MS` 当初要解决的问题。

## 五、失败模式

| 情况 | 表现 | 处理 |
|---|---|---|
| NAS 出网断了 | 解析失败 | 入队时明确报错"曲库连不上"，队列里不落条目；已在播的那首靠磁盘缓存继续放 |
| 上游签名过期（~2h） | 拉流 404/403 | 解析缓存只在 10 分钟内复用；磁盘缓存命中时不碰上游 |
| 稿件被删/需大会员 | 解析无音轨 | 复用 `MUSIC_ONLINE_NO_AUDIO_MESSAGE` 文案 |
| 磁盘写满 | tee 失败 | catch 后纯代理，日志 warn 一次 |

## 六、验收标准

1. 两人（或两个角色）在同一个厅：A 把在线曲目排进队列，B 的界面无需刷新出现该曲目并同步播放，偏差进入既有 40ms 死区。
2. 同一首第二次播放：上游命中 0（磁盘缓存生效），首字节来自磁盘。
3. 文件曲目行为零回归（`music-room-test` 全绿）。
4. schema v21 → v22 迁移在真库副本上成功，`db-migrate-test` 并发抢锁通过。
5. 降级路径：上游不可达时进队报错、正在播的曲目不受影响。

## 七、回滚

镜像回滚到 `prev-<ts>` 即可：schema v22 对 v21 代码是"多了两列 + 少了外键"，旧代码读 `music_queue` 仍能工作（`node_id` 列名与语义未变），在线条目在旧代码里只会表现为"文件已删除"。
