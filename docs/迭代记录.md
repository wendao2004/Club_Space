## 你画我猜的历史对局：每回合一张画存下来（2026-10-21）

用户要两件事：轮数可以多些、**"每个人画的什么"能在历史对局里看到**。
后者不是加个列表，而是要决定"画"这个东西怎么存。

### 存档为什么单独一张表

`game_rooms.state` 只装"当前这一局"的状态，每次变更整列覆盖写；而"每回合
一张图"是 append-only 的存档，天然是子表。所以新增 `draw_rounds`（v13）：

```
room_id / round_no / turn_no / drawer_id / drawer_name / word / strokes / results
```

`turn_no`（本局第几回合，跨轮累加）是唯一键 —— **不能用 (轮次, 座位)**：
有人中途退房后 players 会变，同一个"第 2 轮第 1 位"可能先后对应过不同的人，
键会撞。

### 存的是"最终那张图"，不是操作日志

画画过程中产生的是 begin/points/clear/undo 的增量流（只在内存里广播）。
存档时把它**折叠成完整笔画**：

- 同一 `strokeId` 的增量合并成一条（一笔一条，点全在）；
- `clear` 之前的全部丢弃，`undo` 弹掉最后一笔。

这样复盘时前端直接照着画就行，不用重放撤销语义；体积也小得多（少 N 份
元数据）。另外设了单回合 6000 点的上限 —— 80 秒的密集涂鸦能上万点，
一局十轮就是几十 MB，而前 6000 点已经能看出整张图。**截断而不是拒绝**：
宁可图不完整，也不要因为"画得太满"丢了整回合记录。

### 时机选在"绘画结束"

`beginReveal` 之后存档：那一瞬间笔画完整、词已公开、谁猜对也已定下。
写入用 `INSERT OR REPLACE`（id = `room:turnNo`），多点调用也只会覆盖同一份。
画家中途退房时词被清空（回合作废）—— 这种回合不存档，没画成的东西不值得留。

### 权限取舍

历史对局**登录即可看**，不限制"只看自己参加过的"。这是社团内部的娱乐记录，
不是私密内容；而限定参与关系会让"我们上礼拜那局"这种最常见的问法查不出来。

### 轮数

上限从 5 放到 10：再多一局就是两三个小时，社团活动撑不住；下限仍是 1
（6 个人画一轮就已经十分钟了）。

### 界面

大厅右上角"历史对局"→ 列表（标题、时间、回合数、前五名）→ 详情左侧回合
列表（谁、画的什么词、第几轮），右侧只读画布重放那一回合的画，下方是
该回合每个人的猜对情况与总分。默认停在最后一回合 —— 大家最想看刚才那张。

### 验证

`draw-room-test` 68 → **90 条**：历史列表带回合数/排名/结束时间、详情里
每回合带词/画家/笔画/结果、**真画一笔再验证存档里确实有那笔（含颜色与点数）**、
轮数上限 10（99 收敛到 10）、未登录 401。`db-migrate-test` 同步到 v13 并
新增"存档表真的建出来了"的断言 —— 只改版本号断言的话，迁移写漏会静默通过。
全量 **36 套件 / 2354 条**。

## 声音、后台通知，以及"不跟手"（2026-10-20）

三条反馈：「斗地主没有提示声，轮到自己了都不知道」「聊天要能感知到，最好是弹窗」
「社团系统有点卡，不跟手」。三件事的根因完全不同，分开说。

### 一、斗地主：从一声都没有，到"轮到你"必须听得见

斗地主此前**一个音效都没有** —— `lib/sfx.ts` 里早有完整的合成器（象棋的落子、
吃子、将军都是它），但斗地主的 store 一次都没调过。牌桌上唯一的反馈是
"出牌中"三个字和状态栏的一句话。

补了六个音，全部现场合成，仓库里仍然不含任何音频文件：

| 动作 | 音色 | 走哪条总线 |
|---|---|---|
| 发牌 | 五记渐弱的"唰" | 业务（正常音量） |
| 出牌 | 一记"啪"，张数越多越沉 | 业务 |
| 炸弹 / 王炸 | 低频轰鸣 + 噪声爆点 | 业务 |
| 要不起 | 两声下行 | 业务 |
| 轮到你叫地主 | 两个柔和上行 | **系统总线（×3）** |
| 轮到你出牌 | 三个上行音 + 高八度泛音 | **系统总线（×3）** |

最后两行走系统总线是刻意的：它们是这个游戏里唯一"错过就要干等"的信号，音量
必须压过其它音；而"出牌""要不起"一局要响几十次，照着象棋落子的响度会很吵。

**关键在触发方式**：所有音效都挂在 `applyRoom()` 这一次状态迁移上，判据是
**边沿**（false → true），不是"当前是不是我的回合"：

- 同一个房间会被 SSE、3 秒轮询、接口返回值重复覆盖好几次，用状态判断每次都响；
- 因此**所有覆盖房间的路径都必须走 `applyRoom`**。原来是 6 处直接
  `this.room = result.room` 的赋值，全部改掉了 —— 绕过它的路径会静默无声，
  而且只在特定操作序列下复现，属于最难查的那类 bug。

出牌音的指纹用**最后一手的 `at` 时间戳**，不是 `history.length`：服务端把
history 用 `slice(-40)` 封了顶，长局里长度恒定不变，任何以长度为准的判断到
第 40 手之后全部失效。这个坑在本文件里已经踩过一次（界面"这一手"高亮）。

页面在后台时，"轮到你"除了响，还补一条系统通知 —— 戴着耳机在别的窗口里，
只靠声音不一定能让人回来。

### 二、聊天：Toast 只在页面上，页面在后台就什么都看不见

聊天本来就有 Toast 和提示音，但 **Toast 画在我们自己的 DOM 里**：切了标签、
最小化、被别的窗口盖住之后，用户什么也看不到 —— 而那恰恰是他最需要被提醒的
时候。

新增 `lib/notify.ts`，做三件事：

1. **系统通知**：`document.hidden || !document.hasFocus()` 时抛一条浏览器通知。
   两个条件都要判：前者是切标签，后者是切到别的应用（这时标签仍然 visible），
   只判一个就会漏掉一半场景 —— 而漏掉的那一半恰好最常见。
2. **标题角标**：`(3) 社团空间`。这是通知不可用时的兜底（权限被拒、非安全上下文）。
3. **favicon 角标**：换成一个带红点数字的 SVG data URI，不再多一次网络请求。

几个刻意的决定：

- **权限只在用户手势里申请**。在"收到消息那一刻"调 `requestPermission()` 会被
  浏览器直接忽略（Chrome 还会记下这次无手势申请）。入口放在两处：第一次打开
  聊天时的一条可点击提示，以及设置 → 声音里的「桌面通知」。
- **系统通知设 `silent: true`**。声音由 sfx 统一负责（它知道自己有没有被静音），
  两边都响就是"叮叮"两声。
- **tag 用会话 id**，同一个人的连续消息互相替换，不在通知中心堆十层。
- **群聊的标题是「群名 · 发送者」**，单聊才是对方名字 —— 同一个群里三个人同时
  说话时，三条"张三"分不出是哪个群。

顺带删掉了 `ToastHost` 里那个"任何 Toast 在后台都发系统通知"的 watcher：
它会把"已出牌""文件已保存"这类几百毫秒就过期的回执也推送到通知中心，一天下来
能把通知栏刷满。现在只有聊天（以及斗地主的"轮到你"）会发。

设置页新增两个开关：**聊天提示音**（与系统音效分开 —— 系统回执和一天几十条的
聊天消息不是一个噪音预算）与**桌面通知**（带权限状态与一键开启）。

### 三、"卡卡的，不跟手"：先量，再改

先写了 `scripts/perf-probe.mjs`：真实 Chrome + CDP，开三个窗口，用
`Input.dispatchMouseEvent` 拖标题栏 60 帧，统计拖拽期间的 rAF 帧间隔。

第一次测出来 **26 fps，p90 = 50ms** —— 确实掉帧。三处成本，按影响排序：

1. **拖拽时每帧重绘 40px 高斯模糊**。窗口有 `backdrop-filter: blur(40px)`，
   而拖动时它背后的内容（壁纸 + 其它窗口）每帧都在变，模糊每帧都要重算。
   拖动期间改为 `blur: none` + 实心底色 —— 只在按下到松开这几百毫秒生效，
   用户注意的是落点而不是材质。非活动窗口的半径也从 40px 降到 12px。
2. **每帧走一遍 Vue 的渲染管线**。原来 `drag = ref({dx, dy})` 驱动 computed
   style，语义干净，但每秒 60 次要重新生成 vnode 树再打 style。改成直接把
   transform 写到 DOM，松手时才写回 store。**注意不要顺手写 width/height** ——
   即使值相同也会把元素标成几何脏，实测这一条就吃掉 4 fps。
3. 细节：壁纸的 `:has(.desktop__wallpaper-photo)` 换成 class 绑定（`:has` 会让
   浏览器在每次 DOM 变动时重新求值，而桌面里 DOM 变动极其频繁）；任务栏的
   时钟 setInterval 从 setup 顶层搬进生命周期。

结果：**33-37 fps，p90 从 50ms 降到 33ms**。无头浏览器是软件渲染，真机有 GPU
合成会更好；相对提升（约 +30%）是可信的。

另外把斗地主的 3 秒轮询改成"SSE 断线时才轮询"：连接正常时服务端会推每一条变化，
全量拉取纯属重复读库，一局牌下来白跑几十次请求。

### 验证

`ui-smoke-test`（真实 Chrome）**308 通过 / 0 失败**，其中新增 20 条：

- **后台通知 7 条**：替换 `Notification` 成探针，断言"发出了、正文对、是 silent
  的、tag 是会话 id"，以及标题与 favicon 的角标。
- **设置页 6 条**：聊天提示音开关存在、默认开、点击后写进本地偏好；桌面通知
  给出明确的权限状态。
- **斗地主 6 条**：进牌桌响"叫地主"、叫地主之后响"出牌"、界面文案同步。
- 频率探针的判据：`playYourTurn` 的高八度泛音 **2637Hz** 在本项目所有音效配方
  里只出现这一次，看到它就等于看到那个音确实响了。只数声源个数是不够的 ——
  开窗、通知、出错都会产生声源。

## 你画我猜：评审团定方案，规则抄思路、代码自己写（2026-10-20）

用户点名做你画我猜，并要求"成立评审团、有开源的直接移植，尽量不从头来"。
评审分两路子代理并行：一路摸清现有游戏基建的接入点，一路调研开源实现的可移植性。
结论先行：**没有任何一个开源实现可以直接移植** —— 但它们的公开规则可以采用，
传输层必须重写。最终是"规则抄思路、代码自己写"。

### 评审的两个关键结论

**一、许可红线（调研路上最容易踩的坑）**

`kalotrapezis/classGame` 的 README 写 MIT、package.json 写 ISC，但 LICENSE 文件
是 **GPL-3**（提交历史里明确写着 "Relicense from MIT to GNU GPL v3"）——
README 是过时信息。GPL 传染，它的代码一行都不能进这个仓库；
`RubStadel/Skribble` 无 license 同理；`ShreyasTS/skribbl-clone` 质量最差且无
license，放弃。它们的**玩法与公式**（计分、提示节奏）是事实性规则，可以采用。
另外摸到一个高质量的补充：`scribble.rs`（663★，BSD-3，可放心翻译），但它是 Go。

**二、画笔数据不能走 state 列**

`game_rooms.state` 每次变更都是**整列覆盖写**，而画笔是 append-only 的无限
增长序列 —— 让它进 state，一局就是把几百 KB 的字符串重写几百次。所以分两层：

- state 列：只存回合状态（谁在画、词、分数、提示、阶段截止）；
- 画笔 + 房内聊天：**进程内存** `Map<roomId, ...>`，通过新接口补发给中途进入
  或刷新的人。重启丢失可接受 —— 丢的只是"正在画的那张图的已画部分"，
  回合状态在库里，扫描器到点照样推进。这也是有意的取舍，不是遗漏。

### 传输层：SSE + HTTP 攒批

四个开源实现全部依赖 Socket.IO 双向通道；本项目是单条 SSE + HTTP。
画笔的方向拆开后正好各得其所：

- **上行**（画笔/猜词/选词）走 HTTP POST，客户端 80ms 攒批合并 ——
  pointermove 一秒上百次，一条一个请求会把服务端打爆；
- **下行**（笔迹广播）走 SSE 的新事件 `draw-stroke`，与状态事件
  `game-draw` 分开（笔迹每秒好几条，渲染路径和状态渲染完全分开）。

安全边界全部在服务端：只有画家能发笔迹、坐标限定 0-1000、颜色必须
十六进制、单批最多 200 点；**词**只对画家 / 已猜对者 / reveal 之后可见，
引擎的 viewFor 与 HTTP 响应两层都在裁剪，draw-test 里按视角逐个断言。

### 移植了什么

| 内容 | 来源 | 性质 |
|---|---|---|
| 计分（猜对者按剩余时间 2000→100，画家拿一半） | skribbl 类通行规则 | 公开玩法 |
| 提示节奏（均匀铺在绘画前 3/4，永不揭示最后一个字，两字词不提示） | 同上 + classGame 的上限公式 | 公开玩法 |
| 选词超时随机选（画家卡住不能让全屋陪等） | classGame | 公开玩法 |
| 重连补发画布（game-sync 思路） | classGame | 思路 |
| 房间 / 账号 / 推送 / 音效 | 本项目现有基建 | 零新增 |

中文词库自建（200+ 词，三档难度），选词标准只有一条：**能在一分钟内用
简笔画表达** —— 全是具体名词、动作和画面感强的成语。

### 验证

- `draw-test`（引擎纯函数）**79 条**：计分/提示公式正反例、阶段机全程、
  视角裁剪逐视角断言；
- `draw-room-test`（HTTP 层）**58 条**：画笔写入口校验（非画家 403、坐标
  越界 400、颜色/点数上限）、猜词计分落位、画家回合内禁文字、画家退房
  回合作废、超时推进（用真库把 phaseEndsAt 改到眼前，不真等 80 秒）；
- `ui-smoke-test` 新增 11 条（总数 321）：真浏览器里选词、用 CDP 鼠标事件
  在画布上拖一笔、断言笔画到达服务端缓冲、浏览器外猜对、公布答案。
- 全量 **36 套件 / 2320 条断言全绿**。

测试自己抓出来的坑：draw-room-test 首版把"房主开始"放在"非房主被拒"之前，
房主成功后 phase 已不是 waiting，非房主那条变成 400 —— 断言顺序本身就是
状态机的文档，写反了就互相拆台；两个新测试的结果行没按 runner 的
`通过 N 失败 M` 格式输出，被判成"进程崩溃" —— 崩溃判定比静默放行严格，
是对的。

## 运维的四个"写着但没做到"（2026-10-20）

评审的 P2 清单里躺着一批"文档说做了、代码里其实没有"的东西。挑出来做掉了。
它们在正常使用中都不响，但每一条都有明确的、能说清日期的发作方式。

### 一、迁移：真正先炸的不是版本号，是 PRAGMA 的顺序

原计划是"3 行"：把版本号搬到写锁里重读。做完发现不够 —— 而且是用测试打出来的。

先写了 `scripts/db-migrate-test.mjs`，起 4 个真子进程同时打开一个**空库**
（在一个进程里调两次 `getDb()` 是串行的，永远撞不上）。第一次跑就红了，
但报的不是预期的 `duplicate column name`，而是：

```
Error: attempt to write a readonly database
    at migrate (db.ts:  CREATE TABLE IF NOT EXISTS schema_version ...)
  errcode: 8
```

**两层根因**：

1. `busy_timeout` 被设在了其它 PRAGMA **之后**。它之前，这条连接遇到别人占着的锁
   会立刻失败，而不是等 —— 而报错是 `database is locked` / `readonly database`，
   看起来像文件权限或文件系统问题。
2. 就算设了也没用：**SQLite 在切换日志模式时不走 busy handler**。
   `PRAGMA journal_mode = WAL` 需要排他锁，别人正在切（或正在迁移）时直接返回
   `SQLITE_BUSY`，`busy_timeout` 在这一步完全帮不上忙。

改法：

- `busy_timeout` 提到**第一个** PRAGMA；
- 切 WAL 前先读当前模式，已经是 WAL 就什么都不做；没切过去就等 50ms 再看
  （最多 20 次）。并发下第一个进程切完，后面的重读即 WAL，安静退出；
- "打开 + 设 PRAGMA + 迁移"整体可重试（只对 `locked|busy|readonly` 重试；
  磁盘只读、文件损坏立刻抛出去 —— 用 5 秒沉默伪装"再等等就好了"是最难查的故障）；
- 版本号在 `BEGIN IMMEDIATE` **之后**重读；库版本高于代码时只告警不抛
  （回滚到 `prev-<ts>` 镜像时，正是"旧代码 + 新库"）。

验证：`db-migrate-test` **12 条**（4 进程并发、之后重开一次、表与触发器齐全、
`schema_version` 只有一行）。加压到 20 轮 × 6 进程、共 120 次并发打开，0 失败。

### 二、心跳不再写库：在线状态本来就不该问数据库

心跳每 25 秒续期一次 `last_seen`，100 条连接就是 4 次/秒的写事务。
但那些写**没有换来任何信息** —— "这个人还连着"是连接表自己就知道的事，比数据库更准。

所以新增 `server/src/presence.ts`，把在线状态拆成两个来源：

| 来源 | 作用 | 成本 |
|---|---|---|
| 进程内的活连接表 | 主依据，精确到毫秒 | 零 |
| 库里的 `presence` 行 | 只在上下线写一次，兜底"进程被 kill -9 时计数残留" | 一天几百次 |

顺带修掉一个真实故障的**根因**：在线判定曾经**只**看 `last_seen` 窗口（60 秒），
而 `touchPresence` 只在连接建立时调一次 —— 于是每个人连上 1 分钟就全体变灰。
当时的修法是"让心跳多写几次库"，真正的修法是把 `connection_count > 0` 当主依据。
现在心跳只做两件事：点查一次会话是否还有效（读）、发一个 SSE 注释行。

验证：`realtime-test` 新增一条守门断言 —— 把库里的在线痕迹**彻底抹掉**
（`last_seen` 老 10 分钟 + `connection_count = 0`），socket 还连着，仍然必须是在线。
谁哪天把判定改回"只看时间窗"，这条立刻变红。

### 三、审计表的 append-only 从注释变成触发器

`audit.ts` 的模块注释从第一版起就写着"在数据库层加触发器禁止 UPDATE/DELETE"。
实际上从来没有这两个触发器 —— 承诺只存在于注释里，"不可删"实际上只是
"我们没写删除接口"。

v12 迁移补上 `audit_log_no_update` / `audit_log_no_delete`。局限仍然如实说：
root 能 `DROP TRIGGER` 再改，所以这不是防 root，是防**应用层出错**
（以后某个手滑的 `DELETE`）。真正的篡改检测还是哈希链。

验证：`health-test` 新增 8 条 —— schema 到 v12、两条触发器都在、UPDATE 被拒、
DELETE 一条被拒、DELETE 全表被拒、被拒后记录还在、**INSERT 仍然放行**
（挡住写入等于把审计功能关掉）。

### 四、证书到期：一个 13 个月后才发作、但发作了就打不开平台的故障

证书签 397 天，到期那天的表现是**所有成员的浏览器同时红屏**，
Service Worker 一起失效 —— 而"打开平台看看怎么回事"这个动作本身就打不开了。

`/api/health` 现在返回 `cert`：`notAfter` / `daysLeft` / `expired` / `warn`。
≤30 天转 `degraded`，但**不变 503** —— 重启修不好一张过期的证书，而 Docker 会把
503 当成"容器坏了"反复重启，真正的线索会被重启日志淹没。

三个实现上的取舍：

- **只挂 `server.crt`，不挂 `server.key`。** 这个容器每天在解析用户上传的文件，
  没有理由让它拿到站点私钥；而证书本身是公开的（每个成员的设备里都装了签发它的根证书）。
- **缓存按 mtime + size 认版本，不按 TTL。** 换证书之后必须在下一次探活就反映出来，
  否则"我刚重签了，怎么还在报 30 天"会白浪费一次排查。
- **`upgrade.sh` 加前置检查。** Docker 遇到宿主机上不存在的挂载文件会**建一个同名目录**，
  之后 openssl 写这个路径必然 `Is a directory`，而报错看不出根因。

验证：新增 `cert-health-test` **12 条**（5 天后到期 → `daysLeft` 落在 3~6、`warn` 为真、
`degraded` 但 HTTP 200；换文件后 `daysLeft > 300`、回到 `ok`；到期时间戳确实变了）。
证书由 `run-all-tests.mjs` 用 openssl **现签** —— 不往仓库里放固定证书，
那种证书会在某一天毫无征兆变红，而代码一行没动。

### 五、三件顺手的小事

- **`.env` 权限**：`upgrade.sh` 每次升级检查，过宽就 `chmod 600` 并说明原因。
  有一个例外必须提示而不能默默改：开了管理员运维时 ops-runner 要把 `.env` 挂进容器，
  600 + 属主不匹配会让运维页每个操作都 `permission denied`。
- **`gen-certs.sh` 的 8443**：查证后确认**早已统一到 9443**，是评审文档没跟上；
  这条按"文档已过期"处理，代码未动。
- **README 的测试数**：从 1801 改成实测值（34 个套件 / 2149 条断言），并把漏记的
  8 个套件补进表里（`xiangqi-bot` / `totp-ratelimit` / `csv-parser` / `office-edit` /
  `health` / `health-degraded` / `cert-health` / `db-migrate`）—— 原来那张表的数字
  早就和套件对不上了，"26 个套件"实际上是 34 个。

## 聊天的最后一公里：加人 / 退群、引用回复、@提醒（2026-10-20）

评审文档里写着"聊天 ~80%，缺 @提醒、引用回复只有后端字段没有前端入口、
建群后不能加人/退群"。这次把这三件事补完，外加一件顺手的安全修补。

### 一、群的成员管理：函数早就写好了，只是没人能调到

`chat.ts` 里 `addMembers` 与 `leaveConversation` 一直都在，但 **`index.ts` 里没有任何路由**，
前端自然也没有入口 —— 和之前记账 store 那些"写 action 全项目 0 调用"是同一类问题：
代码看着齐，功能实际不存在。表现是：建完群就再也改不了成员，想退群只能不用它。

补的是两件事：

1. **两个接口**：`POST /api/chat/conversations/:id/members`（加人）、
   `.../leave`（退群）。都写一条系统消息（"某某 邀请 某某 加入群聊" / "某某 退出了群聊"），
   并推 `conversation` 事件让相关人的列表立刻刷新 —— 否则被拉进来的人要等到下次发消息
   才知道自己多了个群。
2. **界面入口**：成员面板底部加「邀请成员」「退出群聊」。邀请视图列出还没进群的联系人，
   勾选后一次提交；退群要二次确认，并把"退出后这条会话会消失、想回来只能被人重新拉"写清楚。

几处刻意的取舍：

- **任何群成员都能加人**，不是只有群主。内网社团注册要邀请码，风险面很小；
  而"只有群主能加"会让群主一离线群就扩不了。
- **单聊不能加人、也不能退**。单聊退掉在语义上说不通：对方那边会话还在，
  你再发消息就会返回同一个会话（`pair_key` 唯一约束），于是"退了又回来"，
  用户会以为退群失败。所以直接 400 并说明原因，而不是做个看起来能点的按钮。
- **重复加同一个人**不报错、不重复插入、也不再写一条系统消息（`added` 返回空数组）。
  否则群主连点两下就会刷出一串"邀请某某加入"。

### 二、引用回复：快照由服务端给，不由发送者转述

`reply_to` 字段一直存在，`sendMessage` 也一直在收，但前端只有类型定义、没有 UI。

做法上有一个关键决定：**引用块里的"原文"由服务端查出来**，而不是前端把被引用那条的
正文一起发上来。理由有三条：

1. 前端翻历史是分页的，引用的那条可能压根不在当前窗口里；
2. 一条消息要推给 N 个成员，各自查一次就是 N 次请求；
3. 被引用那条如果已撤回，**不能**再显示原文 —— 这个判断只有服务端做得了。

实现上是把四处重复的消息 SELECT 收敛成一个 `MESSAGE_SELECT` 常量（原来发送成功返回、
拉一页历史、取单条、撤回后回读各抄了一份列清单，加字段要改四遍，漏一处就表现为
"发出去时正常、刷新一下引用块就没了"），自连接 `messages` 取被引用那条的
`kind/body/deleted_at` 与发送者名字，`toMessageView` 拼成 `reply` 快照。
被引用消息已撤回时，`preview` 只给"原消息已撤回"，`recalled: true`。

> **顺手堵了一个越权读取**：`reply_to` 是外键但没有任何"同会话"校验。也就是说，
> 只要知道一条消息 id（比如以前是群成员、后来被移出），就能在**自己和别人的单聊里**
> 引用它，把那条原文通过引用块"引"出来。现在 `sendMessage` 先校验
> `reply_to` 属于本会话，否则 400。测试里有一条专门钉这个。

界面这边：消息悬停多一个「回复」，输入区上方出现引用条（Esc 取消），发送后自动收起；
自己的气泡是实心强调色，引用块用半透明白底以免糊在一起。

### 三、@提醒：服务端算，前端不猜

输入 `@` 弹出成员候选（按显示名/账号过滤，上下键选、Tab/Enter 确认），插入 `@显示名`。
消息渲染时把 `@xxx` 标出来，点到自己时用更醒目的底色。

"有人@你"的角标放在**会话列表**上，这个必须服务端算：

- 前端只对**当前打开**的会话有消息实体，其它会话只有 `lastMessage` 一条，扫不出来；
- 而"有人@你"恰恰是没打开的那个会话最需要的提示。

`ConversationSummary` 加 `mentionUnread`，用一条 `GROUP BY conversation_id` 的聚合查询
一次算出所有会话的"未读且 @我"条数（不是按会话逐个查的 N+1）。
匹配用 `instr(body, '@显示名') > 0` 而不是 `LIKE '%...%'`：显示名里出现 `%` 或 `_` 时
LIKE 会把它当通配符，结果是"谁发什么都算 @我"或者永远匹配不到 —— 测试里专门造了一个
名字叫「百分%xxx」的成员来验证。

已读即清：`markRead` 把水位推上去，`mentionUnread` 自然归零；前端在乐观清零时也一并
把 `mentionUnread` 置 0，否则服务端已经是 0、本地还挂着红 @，得等下次全量刷新才消。

### 四、401 全局处理：会话过期不再"假装还登录着"

`api.ts` 的 `request()` 原来不判 401，全站只有 5 处页面自己兜。会话 12 小时过期，
在这台 NAS 上是每天都会发生的事：过期之后点任何东西都只弹一句"未登录"，
而界面还停在已登录状态，用户反复点同一个按钮、每次都失败。

现在 `request()` 统一识别 401，通过注册回调（`setUnauthorizedHandler`，在 `main.ts` 里
装好 pinia 之后注册 —— 直接 import auth store 会和它 import api 形成循环）把界面切回登录页，
顺带断开 SSE。`/api/auth/*` 排除在外：登录页密码输错也是 401，那不是会话过期，
触发全局登出只会把刚填的表单清空。

### 验证

- `scripts/chat-test.mjs` **111 通过 0 失败**（新增 26 条）：非成员加人 403、单聊加人/退群 400、
  重复加人幂等且不再写系统消息、新人进群只看到 1 条未读（就是邀请他那条）、
  退群后读消息 403；引用快照三要素（id/名字/原文）、刷新后仍在、撤回后降级为
  "原消息已撤回"、跨会话引用 400；@提醒的 0/1 变化与已读清零、显示名带 `%` 不误伤。
- `scripts/ui-smoke-test.mjs` **288 通过 0 失败**（新增 20 条）：新群靠 SSE 出现在列表、

  那条系统消息。静默进群的话用户只会看到一个陌生的群凭空出现，反而更困惑。

## 象棋不再卡顿、机器人不再"卡在思考"（2026-10-20）

用户的两句话："玩起来有点卡顿"、"人机被将军有几率卡在思考"。
第一句是**实测出来的硬伤**，第二句是一个**没法稳定复现的状态残留**。分开说。

### 一、卡顿：搜索把整个服务端堵死了

原来的机器人搜索是同步递归、直接跑在主线程上的（`xiangqi-ai.ts` 里那段注释
还专门论证过"为它起 worker 不划算"）。困难档一手棋要跑满 1.2 秒的时间预算，
这 1.2 秒里 Node 进程**完全停摆**。写了个探针在机器人思考期间高频打 `/api/health`：

```
改前：81 次探测  p50 2ms  p90 4ms  p99 1195ms  max 1195ms
改后：81 次探测  p99 5ms   max 5ms
```

也就是说：它思考的时候，你自己点棋子的合法性请求、SSE 推送、别人的聊天、
正在上传的文件，全都在排队等它算完。这不是"感觉卡"，是真的卡。

改法是把搜索搬到 worker 线程（`games/bot-runner.ts` + `games/xiangqi-worker.ts`）：

- 主线程只负责收发消息，棋盘用序列化字符串传递（90 格的对象数组做结构化克隆
  比一行字符串贵得多）；
- **失败必须能退化**：worker 起不来（部署环境不支持、线程 OOM）就退回主线程直接算，
  慢一点但功能还在；
- **不能无限等**：单次任务超时（时间预算 + 5 秒余量）就换线程，换两次还不行就
  永久退回主线程；
- **排队不并发**：一台 NAS 上同时开几局是常态，但搜索是纯 CPU 活，并行只会让
  每一手都变慢。一个线程串行消化队列，留核给 HTTP 与 SSE；
- 空闲 `unref()`、有任务 `ref()`：既不阻止 SIGTERM 后正常退出，也不会让在途
  任务的 Promise 悬着。退出流程里也补了 `shutdownBotRunner()`。

顺带把"思考节奏"和搜索**并行**了：原来先等 500ms 再算 1.2 秒，用户等 1.7 秒；
现在落子那一刻就开始算，只是不允许早于 500ms 落地 —— 困难档实际等待 1.2 秒。

### 二、卡在思考：后台落子链断了，没人知道

"电脑正在思考…"这个状态是 `status==='playing' && turn===botSide` **算出来的**，
它本身不会超时。所以只要后台那条链（定时器 → 搜索 → 按人推送）任何一环断掉，
界面就永远停在那一句话上，而且服务端日志里可能只有一行 `console.error`。

原来至少有两个真实的断点：

1. `makeBotMove` 在"无棋可走"时**安静地返回 null**，注释写着"交给上层判终局" ——
   而上层只是 `if (!result) return`。于是房间永久停在"该电脑走"。
2. `chooseMove` 给出的着法如果不在权威 `legalMoves` 里（两份走法生成实现在某个
   冷门局面上分叉），`applySideMove` 会抛 400，被 catch 掉 —— 同样是永久卡住。

现在有四道出口，任何一道生效都不会让对局冻住：

- **无棋可走 → 自己判终局**（`finishWithoutMoves`），并把结果按人推到两端屏幕上
  （走的是 `game` 事件而不是 `game-move`，因为没有"落子"可推）；
- **落子前用权威引擎复查一次**：不在合法表里就换一步合法棋，把 400 挡在落子之前；
- **失败重试一次（跳过搜索直接挑一步合法棋）**，两次都失败才是真异常；
- **看门狗**（`healStalledBotTurn`）：拉取房间时如果发现"该电脑走"已经超过 8 秒、
  且进程里没有排队中的落子任务，就重新排一手。前端配一个 6 秒的客户端看门狗
  （`GamesApp` 里），显示"思考中"太久就主动重新拉一次房间 —— 于是这条路径天然闭合：
  用户不需要刷新页面，更不需要重启服务。

还顺手修了一个只在异步化之后才会暴露的问题：搜索期间（现在是真异步了）人可能
已经认输/退出，落子必须**重新读一次库**再写，否则会把"已结束"的对局写回"进行中"。
新增的用例专门验证这一点。

### 验证

新增 `scripts/xiangqi-bot-test.mjs`（12 条断言，已注册进全量套件）：

```
【1】机器人思考期间，服务端照常响应
  ✓ 搜索不再堵住主线程（p99 < 400ms）   81 次探测 p99=5ms max=5ms（改前 max≈1195ms）
【2】连续多手都能应招，且落子合法（10 手，无一次被服务端拒绝、红黑严格交替）
【3】掉了一次调度的房间能自己补上这一手（直接改库造出"该电脑走但没人调度"的状态，
      再拉一次房间 → 服务端自己补上，无需重启/刷新）
【4】搜索期间认输，对局不会被写回进行中（结束原因仍是 resign）
```

已有用例全绿：`xiangqi-test` 69、`xiangqi-ai-test` 36、`xiangqi-mate-test` 11、
`games-test` 84（含人机对战那一段）。

## 在线编辑 Word / Excel：只改内容，版面一个像素都不动（2026-10-20）

上一轮做的是"**看**"（预览），这一轮做的是"**改**"。

这里有一个必须先说清的选择：为什么不上 OnlyOffice / Collabora。它们是真的
在线 Office（协同、格式保真、打印排版都对），但单实例要吃 1-2GB 内存，
而部署文档里白纸黑字写着这台 NAS 留给业务容器的只有 2-4GB，重任务一律按需拉起
（`deploy/heavy-tools.compose.yml` 的整段注释就是这个结论）。把在线编辑做成
"要管理员先手动拉一个 2GB 容器"，对社团日常使用等于没有。

所以走的是**浏览器内编辑 + 内容级回写**：
- 表格用 ExcelJS 打开整份 workbook，只改被点的那一格，保存时把整个 workbook
  序列化回去 —— 样式、公式、列宽、合并单元格都是原样（改一格不会把表头配色抹掉）。
- 文档自己解析 OOXML（`web/src/lib/docx.ts`）：把 `document.xml` 拆成段落 / 列表项 /
  表格 / 只读块，每段记住**原始的 `w:pPr` 片段**；保存时只替换 `word/document.xml`，
  其余部件（styles / numbering / media / 页眉页脚 / 关系表）一个字节都不碰。
  于是"改一句话"之后，页眉、图片、页码、编号样式全都还在原处。

**没建模的东西一律原样保留、界面标只读**（图片、图表、嵌套表格、有合并单元格的表格）。
这是"宁可不让你改，也不能给你改没了"。

**后端只加了一个接口**：`PUT /api/files/:id/content`。它做的是**原地改写**一个已存在的
文件（id / 名字 / 位置 / 权限都不变，目录里不会多出一个副本），四道闸门：
写权限（`canWrite`，不是"能读就能写"）、类型白名单（表格/文档/文本，其余 415）、
大小上限（`WL_MAX_EDIT_BYTES`，默认 32MiB）、磁盘余量（与上传同一道 `assertDiskSpace`）。
存储仍然走内容寻址：新内容按 sha256 落成新 blob，旧 blob 引用数 -1（归零才删盘），
所以"两个节点共用一份内容"时改其中一个不会把另一个弄丢 —— 这条有专门的断言。

**并发用乐观校验而不是锁**：保存时带上打开文件那一刻的 `updatedAt`，
期间被别人改过就回 409，界面给出"重新加载 / 仍用我的版本覆盖"两个选择。
这不是协同编辑（那需要 OT/CRDT 和常驻服务，不在内存预算内），
它的价值是把"会静默丢数据"变成"会告诉你可能丢数据"。

**顺手补了一个一直缺的东西**：窗口关闭守卫（`windows.setCloseGuard`）。
改了没保存就点 × —— 在桌面隐喻里"关窗口"等于"这事做完了"，没人会预期它是"丢弃"。
现在会先问一句，选"继续编辑"就留在原地。

体验上的几处取舍：
- 双击 .xlsx / .docx 直接进编辑器（双击一个表格的人想的是改它）；**预览移到右键菜单**；
- 表格只渲染看得见的那几十行（虚拟滚动），一万行的表打开也不卡；空白表给 50×12 的
  空格子，否则新建出来是一个孤零零的 1×1；
- 打字用"直接敲 = 覆盖这一格"，Enter 换下一行、Tab 换下一列、Ctrl+S 保存；
- 文档里 Enter 新建段落、Backspace 在空段首删段、粘贴一律按纯文本（网页带来的
  内联样式既写不回 docx，也不该污染文档）。

验证：新增 `scripts/office-edit-test.mjs` 26 条（权限 403 / 类型 415 / 冲突 409 /
空内容 400 / 引用计数 / **下载回来用 ExcelJS 解析确认改的那格变了、没改的还在、
加粗和公式都还在**）；`ui-smoke-test` 231 → 268，新增三节在真实 Chrome 里
走完整条链路（工具栏新建 → 动态加载 900KB 的 ExcelJS → 编辑单元格 → 保存 →
**下载回来解析 xlsx / 解压 docx 校对内容**）、一份带标题/加粗/列表/表格的 docx 能不能被**读出结构**，另外验了"有未保存修改时关窗会先问一句"。

> 已知边界（界面上也这么写）：不支持协同编辑；旧版 .doc/.xls 与 .ods/.odt 不给编辑入口
> （浏览器里没有可靠的读写实现，硬做出来的产物十有八九打不开）；文档编辑器编辑的是
> **内容结构**而不是精确版面；图片等未建模内容只读。

## Office/CSV 在线预览：能双击打开的别再静默下载（2026-10-20）

以前双击一个 docx / xlsx，浏览器渲染不了，于是**静默下载一个打不开的文件** ——
功能清单里写着"文件管理"，成员的实际体验却是"这个文件在这儿没用"。
现在两类都能预览，走的是两条完全不同的路：

**CSV / TSV —— 前端自己解析（`web/src/lib/csv.ts`）**
不依赖任何服务端能力，所以转换服务没开也一样能看。用**状态机**解析而不是
`split(',')`：后者遇到 `"联想, 16G, 512G"` 会切成 3 列、遇到字段里换行会整行错位，
行数看着正常、内容全错 —— 是最难被发现的那类 bug。分隔符自动识别时
"列数一致"给 10 倍权重（中文说明里逗号最多，但它在每一行里的次数不稳定）。
表头判定宁可漏认：只有"每格非空且都不像数字"才当表头，认错的代价是第一行数据
变成列名。超过 2MB 或 1000 行就退回纯文本 / 只显示前 1000 行，不让大表卡死标签页。

**Word / Excel / PPT —— 转成 PDF 再预览**
复用已有的 `doc.to-pdf` 工具（服务端 Gotenberg），产物是**真实落盘的文件节点**，
转完直接在同一个窗口里当 PDF 看，另外给了「看原文件」回退。
转换服务是按需拉起的（见 `deploy/heavy-tools.compose.yml`），所以它的"不可用"
是常态而不是故障：界面先问一次工具列表，**不可用就不给那个按钮**，
而是直接把"为什么不能预览 + 管理员该跑哪条命令"写在窗口里 ——
一个点下去必然失败的按钮比没有按钮更糟。

**顺手修掉一个让整条路走不通的 bug**：`server/src/mime.ts` 里 CSV 的判定是
`text.split('\n').every((l) => l.split(',').length > 1)`，而任何以换行结尾的文件
（**几乎所有导出的 CSV 都带**）最后都会多出一个空串，它 split 出来长度是 1，
于是 `every` 恒为 false —— 真实的 CSV 一律被判成 `text/plain`，表格预览永远走不到。
文件照样能传能下能用纯文本打开，只有"预览是表格还是文本"这一处不同，藏得很深。

验证：新增 `scripts/csv-parser-test.mjs` 33 条（直接 import 界面用的那份 `.ts`，
Node 22.18+ 默认剥离类型，跑的不是副本）；`ui-smoke-test` 215 → 231，
新增的两节在真实 Chrome 里上传 CSV 与手写的最小 docx，断言**引号里的逗号没有被切错列**
和**转换服务不可用时没有「转为 PDF」按钮**。

## 启用运维管控：一句过期的提示，三个真问题（2026-10-19）

页面上那句"设置 `WL_ADMIN_DOCKER_ENABLED=1` 与 `WL_ADMIN_TOTP_SECRET`"是**早期设计的残留**：

1. **NAS 上的 `docker-compose.yml` 被改坏了。** 那一行成了
   `${WL_ADMIN_TOTP_SECRET:1}` —— 非法的插值格式（`:1` 不是默认值语法），
   compose 在**解析阶段**就退出，于是 `up -d` 一直失败，但错误信息只有一句

   表现就是"改了 `.env` 没反应"。
2. **执行器在 `admin` profile 里，`up -d` 不会拉起它。** 这是刻意的（持有
   `docker.sock` 的容器不该被顺手带起来），但文档里写的命令是 `docker compose up -d`，
   少一个 `--profile admin` 就永远连不上执行器。
3. **执行器镜像构建在国内网络下会卡死。** `apk add docker-cli` 走 Fastly，
   实测下一个小索引文件要 1 分 45 秒，构建会静默卡住十几分钟看不出在做什么。

   整体构建 2 分 49 秒。已把它做成 `.env` 里的 `WL_APK_MIRROR`。

改动：`docker.ts` 与 `OpsApp.vue` 的提示改成真实条件（开关 + `--profile admin`），
`部署指南` 第 2 步补上 profile 与"必须 `up -d` 不能 `restart`"的说明，

按 `httpRunner` 的同一条路径 POST 到 `http://ops-runner:9119/exec` ——
