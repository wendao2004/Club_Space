# 部署指南（飞牛 NAS）

面向：把社团空间部署到自己 NAS 上的人。全程约 30 分钟，其中一半时间在等镜像和装证书。

---

## 0. 先确认这三件事（做错了后面全白费）

| 检查项 | 为什么 |
|---|---|
| **NAS 内存 ≥ 8GB** | 业务容器实际只有 2-4GB 可用。8GB 是能舒服跑起来的下限：fnOS 自己 + Samba + 相册索引 + 影视转码长期占 2-5GB。 |
| **NAS 的 IP 已做 MAC-IP 静态绑定** | 证书里写死了 IP。IP 一漂移，全站证书告警、Service Worker 注册失败、摄像头和通知全没了。这是整个部署里最容易被忽略、后果最严重的一条。 |
| **NAS 上能跑 `docker compose`** | 飞牛的 Docker 应用或 SSH 都行。整个平台就是两个容器：`caddy` + `app`。 |

---

## 1. 拿到代码并放好

在 NAS 上建一个目录（下面以 `/vol1/docker/wl-club` 为例）：

```bash
mkdir -p /vol1/docker/wl-club
cd /vol1/docker/wl-club
# 把仓库内容放进来（git clone / SMB 拷贝 / U 盘均可）
```

目录结构应该是：

```
wl-club/
├── server/          # 后端
├── web/             # 前端
├── scripts/         # 测试脚本
└── deploy/          # 部署相关（本指南都在这里操作）
    ├── docker-compose.yml
    ├── Caddyfile
    ├── ca/
    │   ├── gen-certs.sh
    │   ├── ca.key      # 根 CA 私钥：600，**不挂进任何容器**，不进 git
    │   ├── ca.crt      # 根证书：644，公开，发给成员安装
    │   └── served/     # 只有这个目录挂进 caddy（server.crt / server.key）
    ├── onboard/
    ├── convert/
    ├── backup.sh
    └── restore-drill.sh
```

> **`ca.key` 和 `server.key` 的区别**：`ca.key` 是根 CA 私钥，拿到它就能伪造
> 这台 NAS 上**所有**服务的证书；`server.key` 只是当前这张服务器证书的私钥。
> 所以 Caddy 容器只挂 `ca/served/`（里面只有 server 证书），
> 根私钥留在宿主机上，容器里连读都读不到。部署完可以验证：
>
> ```bash
> docker compose exec caddy ls -l /certs   # 只应看到 server.crt 和 server.key
> ```

## 2. 生成证书（含 IP SAN）

```bash
cd /vol1/docker/wl-club/deploy/ca
WL_HOST_IP=192.168.1.100 WL_NAMES="wl.club wl.local" ./gen-certs.sh
```

把 `192.168.1.100` 换成你 NAS 的实际 IP。

脚本会：
- 生成 10 年有效期的内网根证书：`ca.key`（**600，只留在宿主机**）+ `ca.crt`（644，公开）
- 生成 397 天有效期的服务器证书到 `ca/served/`：`server.crt`（644）+ `server.key`（600），**SAN 里同时包含主机名、`.local` 名和 IP**
- 生成 iOS 可一键安装的 `.mobileconfig` 描述文件
- 生成 Windows 一键安装脚本
- 把证书和脚本复制到 `deploy/onboard/certs/`（成员下载的是 `ca.crt` 副本，与容器无关）
- **打印根证书的 SHA-256 指纹** —— 把它发到社团群里，让成员安装前核对，防止内网有人做中间人替换证书

脚本对端口有默认值：`WL_HTTPS_PORT=9443`、`WL_ONBOARD_PORT=8080`，与
`.env.example` 一致。**如果 `.env` 里改了端口，跑脚本时也要显式传同样的值** ——
引导页的"进平台"链接就是脚本按这两个值写进去的，对不上会把成员送到错端口。

脚本可以反复跑：
- **根 CA 是幂等的** —— 已有 `ca.key` + `ca.crt` 就原样复用（指纹不变）。
  这是硬要求：换掉根 CA 会让**每一台**装过证书的设备失效，全员重装。
- 服务器证书每次都会重签（同一张根 CA 签的，客户端不会重新报警告），
  换 IP / 换主机名 / 证书到期都靠这个流程。
- 如果两个文件只剩一个（比如误删了 `ca.key`），脚本会**报错停下**，
  而不是补生成一张新的 CA —— 那种"修复"实际会让所有设备失效。

### 已有旧部署升级到新结构（**不要重签**）

旧版本的 `server.crt` / `server.key` 直接放在 `deploy/ca/` 根目录，整个目录都挂进了
Caddy 容器（根私钥也在里面）。升级时把它们搬到 `ca/served/` 即可：

```bash
cd /vol1/docker/wl-club/deploy/ca
# 直接重跑脚本：检测到旧结构会自动 mv 到 served/，不会重签
./gen-certs.sh
```

脚本输出里应能看到 `检测到旧目录结构 ... 迁移到 served/（不重签）` 与
`沿用已迁移的服务器证书`。如果你更想手动搬、不跑脚本：

```bash
cd /vol1/docker/wl-club/deploy/ca
mkdir -p served
mv server.crt server.key served/
chmod 600 served/server.key
chmod 644 served/server.crt
```

然后回到 `deploy/` 重建容器（挂载路径变了，必须 `up -d`，`restart` 不生效）：

```bash
cd /vol1/docker/wl-club/deploy
docker compose up -d
docker compose exec caddy ls -l /certs    # 只应有 server.crt / server.key
```

> **绝对不要为了"升级"重新生成根 CA**：那会让每台成员设备重新弹证书警告，
> 并要求所有人重新安装 `ca.crt`、iOS 用户重新去「证书信任设置」里点一次完全信任。
> 只要 `ca.key` 与 `ca.crt` 还在，证书链就是连续的。

> **为什么证书里必须有 IP**：家用路由器/AP 默认经常开多播过滤，`wl.local`（mDNS）在很多网络里根本解析不了；Android 更是完全不解析 mDNS。所以 IP 直连是唯一 100% 可靠的方式，而要让 IP 访问不弹证书错误，证书就必须包含 IP 类型的 SAN。

## 3. 填访问地址与端口（不改代码，只改 .env）

**这一步不要改 `Caddyfile`。** 它已经参数化了，站点地址与引导页地址都从 `.env` 读。

打开 `deploy/.env`，把这几项按实际情况填好：

```ini
# 主站端口。⚠️ 不要用 443/80 —— 飞牛 fnOS 自己的 nginx 占着 80、443、5666，
# 绑上去会直接 "address already in use" 起不来。
WL_HTTPS_PORT=9443

# 明文引导页端口，成员装证书用的入口
WL_ONBOARD_PORT=8080
# 把 192.168.1.100 换成你 NAS 的实际 IP
WL_ONBOARD_BASE=http://192.168.1.100:8080
```

> **为什么不用主机名匹配**：Caddy 默认按 Host 头匹配站点地址，那意味着
> 请求里的主机名和端口必须**逐字**对得上 —— 换成主机名访问、或端口写错一位，
> 得到的都是 404，而错误信息完全不提"Host 不匹配"。内网平台只有一个入口、
> 一张证书，不需要按名字分流，所以本站配置直接绑端口：任何 Host 都进同一个站。
> 少一个必须保持同步的配置项，就少一类"改了一处忘了另一处"。

> **为什么要改端口**：路由器/系统把 80/443 当自己的地盘是常态。飞牛的 nginx
> 同时听着 80、443、5666 三个端口，全被它占了。所以平台跑在高位端口上，
> 访问地址相应变成 `https://<IP>:9443`。
>
> **部署前先确认端口是空的**：
>
> ```bash
> ss -tln | grep -E ':(9443|8080) '
> ```
>
> 没有任何输出才是好的。**不要假设"高位端口一定空着"** —— 实测中就遇到过
> 8443 被一个自己跑的 code-server 占着，而 compose 报的是
> `failed to bind host port for 0.0.0.0:8443 ... address already in use`，
> 那句话说得很技术，不会告诉你"是被别的服务占了，换一个就行"。
>
> **证书里必须有这个 IP**（见第 2 节），否则浏览器会因为主机名不匹配而告警。
>
> 改了端口之后要**同步重跑一次证书脚本**（它会把新端口写进引导页的配置）：
>
> ```bash
> cd deploy/ca
> WL_HOST_IP=<你的IP> WL_NAMES="wl.local" WL_HTTPS_PORT=9443 WL_ONBOARD_PORT=8080 ./gen-certs.sh
> ```
>
> 根证书会被复用（指纹不变），只有服务器证书和引导页配置重写。

改完这几项之后，`.env` 里的 `WL_DATA_DIR` 也要顺手确认一下 —— 它指向宿主机上
的哪个目录，第 4 节末尾讲属主问题时会用到。

## 4. 配置环境变量

```bash
cd /vol1/docker/wl-club/deploy
cp .env.example .env
```

编辑 `.env`，至少填这两项：

```ini
# 会话密钥。生成方式（**用 openssl 而不是 node** —— NAS 上通常没装 node）：
#   openssl rand -base64 48 | tr -d '\n'
# 任何 32 字符以上的随机串都行。
WL_SESSION_SECRET=把生成的长随机串填在这里

# 数据目录（要用你自己的路径）
WL_DATA_DIR=/vol1/docker/wl-club/data
```

第 3 节的四项地址/端口也要在这里填好。

> **`.env` 绝不进 git。** 后端在生产环境检测不到 `WL_SESSION_SECRET` 会**直接拒绝启动**——这是刻意的：用一个每次重启都变的随机密钥会让所有人反复掉线，而且没人会注意到配置缺失。宁可启动失败，也不要悄悄降级。

### ⚠️ 数据目录的属主必须对上

容器里的进程以 **uid 10001** 运行（见 `deploy/Dockerfile` 的 `USER app:app`），
而数据目录是从宿主机绑定挂载进去的 —— **宿主机上的属主说了算**，
镜像里建目录时做的 chown 会被挂载整个盖掉。

属主不对时容器**能正常启动、健康检查也过**，但一建账号、一传文件就报 500，
因为写不进去。这个失败模式看起来完全不像权限问题。

```bash
sudo mkdir -p /vol1/docker/wl-club/data
sudo chown -R 10001:10001 /vol1/docker/wl-club/data
```

## 5. 启动

```bash
cd /vol1/docker/wl-club/deploy
docker compose up -d --build
docker compose logs -f app
```

看到 `社团空间 后端已启动` 就成了。

**内存自检**（重要，8GB 机器必看）：

```bash
docker stats --no-stream
```

期望看到 `wl-caddy` 约 20-40MB、`wl-app` 约 150-250MB。如果 app 超过 400MB，说明有别的东西在占内存，查一下。

## 6. 创建管理员账号

浏览器打开 **`https://<你的IP>:9443/`**（端口用你第 3 节填的 `WL_HTTPS_PORT`）。

第一次打开会因为证书还没被信任而报警告 —— 先点"继续访问"进去把管理员建出来，
之后按第 7 节把根证书装上，警告就没了。

> **不要试 `http://<IP>:3000/`。** 应用容器**不对外发布** 3000 端口
> （compose 里只有 `expose`，没有 `ports`）—— 它只应该被 Caddy 看见，
> 直接暴露会绕过 TLS 和安全响应头。所以宿主机上根本没有 3000 在监听。

**首次打开会是"创建管理员"界面**——第一个注册的账号自动成为创建者（owner）。这是唯一的免邀请码注册路径；之后所有成员都必须持邀请码入场（内网平台不应该开放注册）。

创建后，去「管理 → 邀请码」生成几个邀请码发给成员。

## 7. 让成员装根证书

把引导页地址发到社团群（**换成你 NAS 的实际 IP 和 `.env` 里的 `WL_ONBOARD_PORT`**）：

```
http://192.168.1.100:8080/onboard
```

> 这个 `/onboard` 路径由 `Caddyfile` 里的一条重定向兜着（`redir /onboard / 302`）。
> 站点根目录是 `/srv/onboard`，所以不加那条重定向的话 `/onboard` 会被解析成
> `/srv/onboard/onboard` —— 一个不存在的目录，直接 404。而所有发给成员的链接
> 用的都是 `/onboard` 这个写法，所以那条重定向不能删。
>
> 发之前也记得把 `docs/证书分发.md` 里所有 `192.168.1.100` 换成你的真实 IP ——
> 那一份是**直接复制给成员**的，写错 IP 成员会连到别人的机器上。

引导页会：
- 自动识别设备类型（iOS / Android / macOS / Windows）并给出对应步骤
- **实时检测证书是否已被信任**（顶部状态点：红色未装、绿色已装并自动跳转到平台）
- 显示根证书指纹供核对
- 特别强调 iOS 那个**两步坑**（装完描述文件还要去「证书信任设置」手动打开完全信任）

> **为什么必须装证书**：`http://192.168.x.x` 不是浏览器的"安全上下文"。不装证书时，摄像头/麦克风/屏幕共享、系统通知、剪贴板、PWA 安装这些**直接不可用**；而且 Chrome 对带证书错误的站点**禁止注册 Service Worker**——那不是体验差，是功能没有。

## 8.（可选）启用管理员运维

**先说风险**：能操作 Docker = 能拿到 NAS 的最高权限。起一个挂载宿主根目录的
privileged 容器就能读到所有数据、改任何配置。所以这个功能**默认关闭**，
而且即使打开，它提供的也不是"任意命令终端"，而是一组枚举好的固定操作。

### 它在设计上做的三件事

1. **不提供网页版命令终端。** 只有「查看容器状态、查看服务清单、查看日志、
   启动/停止/重启指定服务、按模板安装/卸载扩展」这几件事。
   理由：允许输入命令再拦截危险命令这种黑名单思路永远能被绕过
   （`find / -exec sh -c`、`docker run -v /:/host`），只有枚举操作才是可证明安全的。

2. **参数只能来自白名单。** 服务名必须在你配置的清单里，模板名必须匹配目录里的
   实际文件。命令行不经过 shell（参数作为数组传给进程），因此不存在命令注入。

3. **危险面被拆到独立容器。** 持有 `docker.sock` 的是 `ops-runner` 容器，
   它不处理任何用户上传的内容；而处理用户文件的应用容器**没有** socket。
   这样即使格式转换链路被 RCE 攻破，攻击者拿到的也只是一个没有特权的小容器。

### 启用步骤

**第 1 步：生成执行器令牌并写进 .env**

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

```ini
WL_ADMIN_RUNNER_TOKEN=上面生成的值

WL_ADMIN_DOCKER_ENABLED=1

# ⚠️ 只列**deploy/docker-compose.yml 里真实存在**、且停掉也无所谓的服务。
#    默认留空。主文件里只有 caddy / app / ops-runner —— 停 app 或 caddy
#    就失去访问入口，停 ops-runner 就失去运维页本身，所以三个都不该填。
#
# ⚠️ 也不要填 convert。转换服务在另一份编排（heavy-tools.compose.yml）里，
#    运维页固定只操作主文件，填了它只会得到一个点下去必然失败的按钮
#    （no such service: convert）。按需拉起它的命令见下面第 9 节。
WL_ADMIN_ALLOWED_SERVICES=

# 建议填管理员的固定 IP：即使会话被劫持，攻击者从别的机器也用不了
WL_ADMIN_ALLOWED_IPS=192.168.1.20
```

**第 2 步：启动（会多起一个 ops-runner 容器，约 20MB 内存）**

```bash
cd /vol1/docker/wl-club/deploy
docker compose --profile admin up -d
```

> ⚠️ 两个必踩的坑：
> 1. **执行器在 `admin` profile 里，`docker compose up -d` 不会拉起它。** 少了 `--profile admin`
>    的表现是页面一直显示"运维管控未启用"、每个操作都报连不上执行器，而 `WL_ADMIN_DOCKER_ENABLED`
>    明明设成了 1。这是"默认关闭"的设计决定的 —— 一个持有 `docker.sock` 的容器不该被
>    `up -d` 顺手带起来。
> 2. **必须 `up -d`，不能用 `restart`。** `docker compose restart app` 只重启现有容器，
>    容器创建时的环境变量快照被原样保留，改了 `.env` 也不会生效。`up -d` 发现配置变了
>    才会重建容器。

**第 3 步：在网页上绑定两步验证**

打开「运维」应用 → 「两步验证」→「开始绑定」。用验证器 App
（Google Authenticator / 微软 Authenticator / 1Password 等）选择"手动输入密钥"，
填入页面上显示的密钥，然后把 App 里出现的 6 位数字填回去确认。

> **绑定之后，你自己的登录方式会变成两步**：输完口令还要再输一次验证器上的动态口令。
> 这不是麻烦，而是必要的 —— 如果登录只看口令，那么第二因子保护的只是"账号里的某些操作"，
> 而口令泄漏后攻击者能做的事远不止那些。第二因子必须守住"进入账号"这件事本身。
>
> **如果手机丢了**：你将被挡在账号之外。补救需要另一位管理员在 NAS 上执行
> `sqlite3 <数据目录>/app.sqlite "UPDATE users SET totp_secret=NULL WHERE username='<你的用户名>';"`
> —— 这是有意的设计（否则"手机丢了"就等于"2FA 可以随便绕过"）。
> 所以：**建议至少保留两个管理员账号**，并且把启用 TOTP 的时间错开。

绑定是**按人**的：每个管理员各自绑、各自可吊销。秘密加密后存在数据库里
（密钥从 `WL_SESSION_SECRET` 派生），所以单独一份数据库备份不足以还原出秘密。

**第 4 步：验证**

在「运维 → 运维操作」里执行「查看容器状态」（只读，不需要动态口令）。
如果能看到容器列表，说明整条链路通了。

### 安全建议

- **`WL_ADMIN_ALLOWED_SERVICES` 尽量短。** 每多一个可停的服务就多一个"手滑把平台搞挂"的机会。
- **配 `WL_ADMIN_ALLOWED_IPS`。** 这是很便宜的一道防线。
- **不要为了省事而绕过 TOTP。** 代码里没有"跳过二次验证"的开关 ——
  这是刻意的，有开关就一定会被打开。
- **定期看审计日志**（管理 → 审计日志）。所有运维操作与被拒绝的尝试都会留痕，
  后者尤其值得注意：它可能是有人在试探边界。
- **扩展模板要自己审。** 平台不会从网络下载模板 —— 能往 `deploy/templates/`
  写文件的人本来就已经有 NAS 访问权限了。

### 已知限制

**这条路径只在 NAS 上才能真实验证**：本项目的开发环境没有 Docker，
所以"docker 命令真的跑通"没有经过端到端验证。我验证的是它的安全逻辑
（权限门禁、参数白名单、命令构造、审计）与执行器自身的白名单校验 ——
这些都通过可注入的执行器在本地完整覆盖了（`scripts/admin-test.mjs` 71 项、
`scripts/ops-runner-test.mjs` 43 项）。第一次在 NAS 上启用时请按上面的
「第 4 步：验证」走一遍。

## 9.（可选）启用格式转换

> **转换服务不能从运维页启停。** 它不在 `deploy/docker-compose.yml` 里，而在下面这份
> 独立的、按需拉起的编排里；运维页（第 8 节）固定只操作主 compose 文件。
> 所以 `WL_ADMIN_ALLOWED_SERVICES` **不要填 `convert`** —— 那会让界面出现一个
> 点下去必然报 `no such service: convert` 的按钮。转换服务按下面的命令手动拉起。
>
> 运维页里如果确实点了这个（旧配置留下的白名单），失败信息里会直接把下面这条命令
> 写出来，不会只给一句 `No such service`。

默认情况下「转为 PDF」显示为**未启用**并说明原因——因为 LibreOffice 单实例要 1-2GB 内存，不能常驻。

需要时按需拉起：

```bash
cd /vol1/docker/wl-club/deploy
docker compose -f docker-compose.yml -f heavy-tools.compose.yml --profile convert up -d
```

然后编辑 `.env`：

```ini
WL_CONVERT_SERVICE_URL=http://wl-convert:3000
```

**改完 `.env` 必须用 `up -d` 重建容器，不能用 `restart`：**

```bash
docker compose -f docker-compose.yml -f heavy-tools.compose.yml --profile convert up -d
```

> ⚠️ 这里是个很容易踩的坑：`docker compose restart app` 只是把现有容器重启一遍，
> **不会重新读 `.env`** —— 容器创建时的环境变量快照被原样保留。所以改完
> `WL_CONVERT_SERVICE_URL` 再 `restart`，工具集里「转为 PDF」依旧显示"未启用"，
> 而你会以为是自己配错了。`up -d` 才会比较配置差异并重建容器。

工具集里的「转为 PDF」这时会变成可用。转换请求走的是
`POST http://wl-convert:3000/forms/libreoffice/convert`（Gotenberg 的标准路由），
中文字体已经烤进镜像，不会出现方框或丢字。

> **两种"不能用"是不同的两件事，别混为一种：**
> - **没配 `WL_CONVERT_SERVICE_URL`** → 工具集里直接显示「未启用」并说明原因（不需要点）。
> - **配了地址但容器已经停了** → 工具集里仍然显示「可用」（可用性只看地址有没有配），
>   点下去任务会失败并明确报「连不上转换服务（地址）」+ 上面那条拉起命令。
>
> 所以"转换完停掉容器"之后，工具集里那一项不会自己变灰 —— 这是有意的：
> 它没有谎报"能用"，只是把失败原因留到真正需要转换的时候再告诉你。

**转换完记得停掉，把内存还给 NAS：**

```bash
docker compose -f docker-compose.yml -f heavy-tools.compose.yml --profile convert stop convert
```

> ⚠️ 结尾那个 `convert` 不能省。`docker compose stop` **不带服务名时会停掉这个项目里
> 所有服务** —— 包括 `caddy` 和 `app`，也就是整站下线。你要的只是停那一个重任务容器。
>
> 同理，`up` 也建议带上服务名（`... up -d convert`），避免顺手把别的东西重建了。

> 转换镜像里**已经烤进了 Noto Sans CJK 中文字体**。这一步是必需的——官方 Gotenberg 镜像没有 CJK 字体，转中文 Word 会得到方框或丢字。

## 10. 配置备份

复制 `backup.sh` 到 NAS，配一个**离开 NAS 本体**的备份目标（外接 USB 盘 / 另一台机器），然后用 cron 每天跑。

**先装依赖**（备份脚本靠 sqlite3 命令行做一致性快照，而平台本身不需要它，
所以一台正常运行的 NAS 上很可能根本没装）：

```bash
sudo apt-get update && sudo apt-get install -y sqlite3 rsync
```

**把变量写进 crontab 文件本身，不要写进 shell 环境：**

```bash
crontab -e
```

```
WL_DATA_DIR=/vol1/docker/wl-club/data
WL_BACKUP_TARGET=/mnt/usb-backup
0 3 * * * /vol1/docker/wl-club/deploy/backup.sh >> /vol1/docker/wl-club/backup.log 2>&1
```

> ⚠️ 这里有两个坑，都会导致**备份从来没跑过而你毫不知情**：
>
> **一、cron 不读你的 shell 环境。** 它执行任务时只注入 `SHELL`/`HOME`/`PATH`
> 等寥寥几个变量，不会 source `~/.bashrc` 或 `~/.profile`。所以"在 SSH 里 export 一下"
> 或"写进 .bashrc"对 cron 都无效 —— 脚本会在第一道硬闸门
> （`WL_BACKUP_TARGET` 为空）直接 exit 1。必须像上面那样写在任务行的**前面**。
>
> **二、`/var/log` 你写不进去。** 以普通用户身份建的 crontab，重定向也以该用户身份
> 执行，而 `/var/log` 属于 root。重定向会在**脚本启动之前**就失败，
> 于是脚本压根没被执行 —— 不是跑失败，是没跑。日志放到你自己能写的目录里。
>
> 配完第二天早上确认一次：`tail /vol1/docker/wl-club/backup.log`，
> 以及 `ls /mnt/usb-backup/` 里确实出现了带时间戳的目录。

`WL_BACKUP_TARGET` **必须是外接盘或另一台机器**。脚本会拒绝两类目标：
不是挂载点的目录，以及与数据目录**在同一台设备上**的路径
（比如 `/vol1/backup` —— 它是挂载点，但和数据在同一块盘上，
盘坏了两个一起没）。确实知道自己在做什么时，用
`WL_BACKUP_ALLOW_SAME_DEVICE=1` / `WL_BACKUP_ALLOW_UNMOUNTED=1` 显式跳过。

**脚本第一件事就是检查备份目标是否在线，不在线就直接失败告警**——绝不在本地悄悄生成一份"假备份"让人以为有备份。这是评审团指出的一个经典陷阱：写在同一个卷上的 `restic` 仓库不算备份。

**每月跑一次恢复演练**：

```bash
./restore-drill.sh /mnt/usb-backup/wl-club-20261016-030000
```

它会真的把数据库打开、校验完整性、逐个核对内容对象是否存在。**没演练过的备份不算备份。**

## 11. 升级

```bash
cd /vol1/docker/wl-club
git pull            # 或在别处准备好新代码再拷进来
cd deploy
docker compose up -d --build
```

升级前先备份一次。数据库迁移是自动的（`schema_version` 表驱动），但迁移一旦发布就只增不改。

> **从旧版本升级（证书目录结构变了）**：这一版的 `docker-compose.yml` 只挂
> `./ca/served`，不再挂整个 `./ca`。如果 NAS 上还是旧结构（`server.crt` /
> `server.key` 在 `ca/` 根目录），`git pull` 之后 `docker compose up -d` 会失败：
> Caddy 找不到 `/certs/server.crt`（容器起不来或证书加载失败）。
>
> 在 `up -d` 之前先跑一次证书脚本，它会把旧文件**原样搬进 `served/`，不重签**：
>
> ```bash
> cd /vol1/docker/wl-club/deploy/ca
> ./gen-certs.sh          # 看到"迁移到 served/（不重签）"就对了
> cd ..
> docker compose up -d
> docker compose exec caddy ls -l /certs   # 只应有 server.crt / server.key
> ```
>
> 详细说明见第 2 节末尾「已有旧部署升级到新结构」。

## 日常运维速查

| 要做的事 | 命令 |
|---|---|
| 看日志 | `docker compose logs -f app` |
| 看内存 | `docker stats --no-stream` |
| 重启 | `docker compose restart app` |
| **改了 .env 之后让它生效** | `docker compose up -d app`（`restart` 不会重读 .env） |

## 出问题时

| 现象 | 原因 | 处理 |
|---|---|---|
| 打不开，或一直转圈 | app 容器没起来 | `docker compose logs app` |
| 提示不安全 / 证书错误 | 成员没装根证书，或装了一半 | 打开引导页看状态点，iOS 特别注意第二步 |
| 摄像头/通知/剪贴板不可用 | 同上，且用户点了"继续访问" | 装证书，然后**完全重启浏览器** |
| 上传大文件到一半断了 | 正常，可续传 | 重新选同一个文件，会从中断处继续 |
| 「转为 PDF」灰色不可点 | 转换服务未启用（设计如此） | 见上面第 9 节 |
| 运维页点「启动服务」报 `no such service: convert` | 白名单里填了主 compose 里不存在的服务 | 从 `WL_ADMIN_ALLOWED_SERVICES` 里删掉 `convert`，按第 9 节手动拉起转换服务 |
| 运维页每个操作都报 permission denied | `WL_DOCKER_GID` 与宿主机 docker 组不一致 | `getent group docker \| cut -d: -f3` 的结果填进 `.env`，再 `docker compose --profile admin up -d ops-runner` |
| 运维页报「无法连接执行器」 | ops-runner 没起，或两边令牌不一致 | `docker compose --profile admin up -d`，核对 `WL_ADMIN_RUNNER_TOKEN` |
| app 容器被 OOM 杀掉 | NAS 内存被别的服务吃满了 | `docker stats` 看看谁在占；或加内存 |
| 平台整体变慢、存储也卡 | 重任务在抢 IO/CPU | 停掉转换容器 |
